domain-modeling

把敲定的术语和不可逆决定当场写到 CONTEXT.md / docs/adr/——域模型的生产侧。

用途与核心区分

domain-modeling 是 域模型的生产侧。它和"读 CONTEXT.md 用词"是两件事—— "This skill is for when you're changing the model, not just consuming it."

5 个动作（during the session）

图 2 · 5 个动作循环：动作 1-4 评估现状，动作 5 落到文件

动作 5（写文件）的特殊性

  • 敲定就写——不攒批、不写"等会再补"
  • 懒创建——文件不存在时，第一个敲定的术语触发创建
  • 就地改——不另存 v2 / 旧版 / 备份

懒创建原则

"Create files lazily: only when you have something to write."
情况行为
没 CONTEXT.md，第 1 个术语敲定 创建 CONTEXT.md
没 docs/adr/，第 1 个 ADR 需要 创建 docs/adr/
已有 CONTEXT.md，新增术语 追加到现有文件
术语冲突 / 推翻原定义 就地改 + 必要时建 ADR 记录原因

这跟 setup-matt-pocock-skills 的"不主动建 CONTEXT.md"是同一原则——文档从需求长出来，不预填。

CONTEXT.md 边界

"CONTEXT.md should be totally devoid of implementation details."
"It is a glossary and nothing else."
✅ 允许❌ 禁止
术语定义实现细节（函数名 / API 形状 / DB schema）
同义词、避免词spec（"系统应该这样工作"）
概念边界（X 是 Y 的子类 / 不是）scratch pad（"等会再想想"）
跨代码一致性约束实现决定（"用 Postgres"——这是 ADR）
概念示例（用户场景）完整业务规则

判断测试："这段写下来，下个不同 codebase 接手时还要不要看？" 不要 → 不放 CONTEXT.md。

与 grilling 的协作

图 4 · grilling (蓝) 与 domain-modeling (橙) 交错工作，文件写入 (橙虚线)

关键点：

  • grilling 问，domain-modeling 写——两条平行轨道
  • domain-modeling 在对账时常发现冲突，触发新 grilling 问题
  • 每次落档都在用户答完后立即发生（不攒批）

被谁调用

调用方方式节奏
grill-with-docs 同步（Skill 调两次） 每轮用户答完 → 立即触发动作
improve-codebase-architecture 独立 扫描代码时按需触发
grilling / grill-me 不调本 skill（纯对话）

用户也可直接触发（适合"我要梳理现有 CONTEXT.md"场景）。
