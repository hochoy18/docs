to-spec

把当前对话压成一篇 spec，发到 issue tracker 上挂 ready-for-agent——不再采访，只合成。

用途

to-spec 是主流程上 "聊完 → 立项" 的桥。 它的本质是 synthesis（合成），不是 interview（采访）——SKILL.md 第一句明说："Do NOT interview the user; just synthesize what you already know"。

它和 grill-with-docs 的分工：

grill-with-docs to-spec
做什么 问问题，提炼共识 把共识写下来
产物 CONTEXT.md / ADRs（私人笔记） 一个公开的 spec issue
对用户的态度 不停追问 不再打扰
调用次数 2 次 skill（grilling + domain-modeling） 0 次 skill，全靠当前上下文

关键：如果觉得信息不够，那是 grill-with-docs 没做透，不要靠 to-spec 来补。

三步流程

图 2 · 三步：探索 → 划 seams → 写并发布（seam 确认是 back-loop）

第 1 步：探索仓库

用 CONTEXT.md 的词汇；尊重 docs/adr/ 里相关区域的现有决定。如果刚刚 grill-with-docs 聊完，这一轮已经做过，可以跳。

第 2 步：划 seams（关键！）

决定测试要插在哪一层。原则：

  • 优先复用已有 seam——别为这个 spec 创造新 seam
  • 能高就高——高层 seam 测得更宽，重构时更稳
  • 理想数量 = 1——seam 越少越好。一个就够
  • 必须 跟用户确认——seam 是后续实现的核心约束

第 3 步：写 spec → 发布

按 6 段模板填完，发到 issue tracker（GitHub / GitLab / local markdown，看 docs/agents/issue-tracker.md 的设置）。直接贴 ready-for-agent 标签，不再额外 triage——spec 本身就是给 agent 看的。

This skill takes the current conversation context and codebase understanding
and produces a spec. Do NOT interview the user; just synthesize what you
already know.

The issue tracker and triage label vocabulary should have been provided to
you. If not, tell the user to run `/setup-matt-pocock-skills`.

## Process

1. Explore the repo to understand the current state of the codebase, if you
   haven't already. Use the project's domain glossary vocabulary throughout
   the spec, and respect any ADRs in the area you're touching.

2. Sketch out the seams at which you're going to test the feature. Existing
   seams should be preferred to new ones. Use the highest seam possible. If
   new seams are needed, propose them at the highest point you can. The
   fewer seams across the codebase, the better - the ideal number is one.

   Check with the user that these seams match their expectations.

3. Write the spec using the template below, then publish it to the project
   issue tracker. Apply the `ready-for-agent` triage label - no need for
   additional triage.

六段模板

图 3 · 6 段模板 — 前 3 段用户视角，中间 1 段工程师决策，最后 2 段测试 + 边界

各段详解

① Problem Statement

用户视角描述问题。不要写"系统慢"，要写"客户提交订单后 5 分钟才收到确认邮件，期间一直焦虑是否成功"。

② Solution

用户视角描述解法。同样不要讲技术——讲结果。

③ User Stories

越长越好。覆盖所有角色、所有用例、所有边界。每条都按这个格式：

1. As an , I want , so that

例：

1. As a mobile bank customer, I want to see balance on my accounts,
   so that I can make better informed decisions about my spending

④ Implementation Decisions

这部分给实现 agent 看。可以包括：

  • 要建 / 改的模块
  • 模块的接口
  • 开发者的技术澄清
  • 架构决定
  • Schema 变更
  • API 契约
  • 具体交互

严禁写具体文件路径 / 代码片段——这些会过时。
唯一例外：/prototype 跑出的、能比文字更精确表达决策的片段（状态机、reducer、schema、类型 shape）可以内联一句，并标注"来自 prototype"。

⑤ Testing Decisions

  • 什么算好测试：只测外部行为，不测实现细节
  • 测哪些模块
  • 类似先例（仓库里现有测试哪些长得像要写的）

⑥ Out of Scope + Further Notes

Out of Scope 写清楚不做什么——避免实现 agent 跑偏。Further Notes 是兜底段。

seams：测试切口

Seam 是 to-spec 里最容易被低估的一步。它 不进 spec，但决定了实现的测试结构。

图 4 · seam 层次 — 选最高的那层

为什么 seam 是关键：seam 决定了实现阶段的测试架构。一旦确定，实现 agent 就要按这个切法建测试。Spec 里只写一句"测试 seam 设在 X 层"，实现就不会乱跑。

何时用 / 不用

用 to-spec

  • grill-with-docs 已经聊透，想正式立项
  • 已经决定要做的功能，想给后续 agent 一份清晰的输入
  • 想要 GitHub / GitLab issue 形式的 spec 留档

用 to-tickets 而不是 to-spec

  • spec 已经存在，想 拆成多个 ticket 分给多个 agent
  • spec 是分阶段的（tracer-bullet），不是单块的

用 prototype 而不是 to-spec

  • 设计问题在对话里解决不了，需要看代码跑起来什么样
  • 答案明显是 throwaway code 就够，不需要完整 spec

用 wayfinder 而不是 to-spec

  • 想法太大、跨多 session、地图还没画出来
  • 先 wayfinder 把决策 tickets 解完，再 to-spec 收口

不要用 to-spec

  • 信息还不够 → 先回 grill-with-docs
  • 已经动手写代码了 → spec 应该先于代码
  • 只是 bug 修复 → 用 /triage → /diagnosing-bugs
