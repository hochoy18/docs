grill-with-docs

把 grilling（采访）和 domain-modeling（落档）捆在一起的 6 行 wrapper。

用途

grill-with-docs 是 ask-matt 主流程的第一站——"idea → ship" 的入口。 它做的事只有一件：调两次 Skill tool，把"问"和"记"两个引擎同时启动。

它的 description 字段定调："A relentless interview to sharpen a plan or design, which also creates docs (ADR's and glossary) as we go." —— interview + 边聊边写文档，一句话讲完。

它自己几乎不做任何事。 所有规则都在 grilling 和 domain-modeling 里——它只是同时叫它们俩。

SKILL.md 全文

整个文件就 6 行有效内容（前面 5 行 frontmatter + 1 行调用指令）：

---
name: grill-with-docs
description: A relentless interview to sharpen a plan or design,
  which also creates docs (ADR's and glossary) as we go.
disable-model-invocation: true
---

Call the Skill tool twice, for "grilling" and "domain-modeling".

没有"如何运行"的步骤——整个 skill 文件本身就是个指令：执行 `grilling` 和 `domain-modeling` 各一次。

组合两个子 skill

图 1 · grill-with-docs 自身是个空壳，两个子 skill 才是真正的活

disable-model-invocation

disable-model-invocation: true 是 frontmatter 里最关键的一行。它的含义：

值谁能调它
false（默认） 用户 + 其他 skill 通过 LLM 触发
true（本 skill） 只有用户显式 /grill-with-docs 触发
图 2 · 用户能直接调，其它 skill 不能静默拉起

为什么要这个标志？

  • grilling 风格的"relentless"采访消耗大量用户注意力——不该被某个上游 skill 静默拉起
  • domain-modeling 会改用户仓库的 CONTEXT.md——属于"用户能编辑"的层级，需要显式同意
  • 让用户保留对"什么时候开始 grill"的完全控制

对比：/triage 没这个标志（issue 分拣是机械的，可以被自动化流程触发）；/diagnosing-bugs 也没（bug 修复是响应式的，不需要用户全程监督）。

复杂度 需要上下文（仓库） 无上下文依赖

对照选择

  • 在 GitHub repo 里打磨设计 → /grill-with-docs
  • 纯聊天、问"这个想法怎么样"、无目录 → /grill-me
  • 想自动化 issue 处理 → 都不要用**（这俩都是用户独占）

它不做什么

  • 不替你拍板——决策在 grilling 的 frontier 里等用户答
  • 不主动建 CONTEXT.md——由 domain-modeling 按需懒创建
  • 不规划原型——写代码让 /prototype 接力
  • 不写 spec——那是 /to-spec 的活
  • 不在多会话构建里调度——那是 /to-tickets 的活
