to-tickets

把 spec / 计划 / 对话拆成 tracer-bullet tickets，每条带 阻塞边，发到 issue tracker。每个 ticket 一个 fresh context window。

用途

to-spec 出来是一整篇 spec；to-tickets 把 spec 拆成 多条小 ticket， 每条带显式依赖关系（哪个必须先做完），然后发到 tracker 上让 agent 各拿各的做。

to-spec to-tickets
产物 1 篇 spec = 1 个 issue N 个 ticket = N 个 issue（或文件）
粒度 完整功能描述 单 context window 内可完成的薄片
依赖关系 不显式画 显式 DAG（每条 ticket 列 Block by）
谁来做 用户审一次后交给实现 agent 每个 ticket 一个 agent session
互动 纯 synthesis，不采访 第 4 步 跟用户对题（粒度/阻塞）

关键概念组合：

  • vertical slice —— 每条 ticket 端到端穿过各层
  • blocking edges —— 显式 DAG
  • frontier —— 所有 blocker 已 done 的 ticket 集合

五步流程

图 2 · 五步 + 步骤 4 的回环（quiz 可能要求重切）

第 1 步 · 收集上下文

从当前对话直接拿；如果用户传参（spec 路径 / issue 号 / URL），fetch 完整 body + comments。

第 2 步 · 探索仓库（可选）

用 CONTEXT.md 词汇；尊重 docs/adr/ 里相关决定；特别要找预重构机会——"先让变更容易，再做容易的变更"。预重构单独成 ticket，先做。

第 3 步 · 起草垂直薄片

每片带 blocked by。没 blocker 的 ticket 可以立刻开始。

第 4 步 · 跟用户对题（必做）

把列表给用户：每条 ticket 显示 标题 / Blocked by / What it delivers。问：

  • 粒度对吗？（太粗 / 太细）
  • 阻塞边对吗？（每条 ticket 真的只依赖真正 gate 它的吗）
  • 要合并 / 再拆吗？

迭代到用户批准。回环回第 3 步调整。

第 5 步 · 发布

按 tracker 类型走不同形态——见后面"发布形态"段。

# To Tickets

Break a plan, spec, or conversation into a set of **tickets**: tracer-bullet
vertical slices, each declaring the tickets that **block** it.

The issue tracker and triage label vocabulary should have been provided to
you. If not, tell the user to run `/setup-matt-pocock-skills`.

## Process

### 1. Gather context
Work from whatever is already in the conversation context. If the user
passes a reference (a spec path, an issue number or URL) as an argument,
fetch it and read its full body and comments.

### 2. Explore the codebase (optional)
... Look for opportunities to prefactor ...

### 3. Draft vertical slices
- Each slice cuts a narrow but COMPLETE path through every layer
- A completed slice is demoable or verifiable on its own
- Each slice is sized to fit in a single fresh context window
- Any prefactoring should be done first

[Wide refactor paragraph: expand–contract pattern]

### 4. Quiz the user
Present the proposed breakdown as a numbered list.
- Title
- Blocked by
- What it delivers

### 5. Publish
- Local → `.scratch//issues/-.md`
- Real tracker → one issue per ticket, native blocking / sub-issue
- Apply `ready-for-agent`

vertical slice 规则

vertical slice = 切功能；horizontal slice = 切层。to-tickets 强制 vertical。

图 3 · vertical slice = 端到端薄片，horizontal slice = 按层横切（不允许）

vertical slice 的硬性规则

  • 每片窄但 COMPLETE：穿过 schema / API / UI / tests
  • 完成一片就 demoable / verifiable
  • 大小 = 单 fresh context window（smart zone，~150k tokens）
  • 预重构先做（第 2 步识别出来，独立成 ticket，先做）

tracer bullet 是什么

Tracer bullet 是 vertical slice 的极端形态——一条最细但端到端可见的轨迹，让整个 stack 跑起来。早期几条 tracer bullet 就是为了证明架构成立（比如最小化的"/api/ping + 前端 fetch + 显示结果"）。

阻塞边 / DAG / frontier

每张 ticket 声明 Block by——它必须等哪些 ticket 先做完。没 blocker 的可以立刻开始。

全部 blocker 都 done 的 ticket 集合 = frontier（前线）。日常节奏就是 work the frontier。

图 4 · T01/T02 已 done → T03/T04 进 frontier。完成它们推进到 T05/T06/T07

frontier 是什么

任意时刻，可以立刻开干的 ticket 集合。它的 size 是并行度上限——如果 frontier = 1（线性链），就只能串行；如果 frontier = 3，可以并行。

work the frontier

完成 frontier 上的一张 ticket，就让它的 successors 进 frontier。线性链上就是 top → bottom；并行图上就多个同时开。

不要做的事： 不关、不改 spec issue（parent）。to-tickets 是把 spec 拆票，不是改源头。

wide refactor 例外

不是所有变更都能切薄片。wide refactor：

  • 一个机械变更（重命名列、改类型）
  • blast radius 横跨整个代码库
  • 单次编辑击碎上千个调用点
  • 任何 vertical slice 都做不到 green（中间态整体编译/测试失败）

这种情况不进 tracer bullet 流程，按 expand–contract：

图 5 · expand → migrate（按 blast radius 分批）→ contract

当分批也保持不住 green

如果分批后单批自己保持不住 CI green（green 只能在最终态保证），就让它们 共用一个 integration branch，所有 batch 共同 block 一个 integrate-and-verify ticket——green 只在那里保证。

判断标准："单批保持不住 green" 是罕见但合法的——只能靠 integration branch + 最终 integrate ticket 来救。绝大多数情况仍坚持 "每批单独 green"。

按 tracker 类型走不同物理形态——tickets 内容一致，只是阻塞关系的物理表示不同。

纪律：no file paths / no code

跟 to-spec 一致：不放文件路径 / 不放代码片段（会过时）。唯一例外：prototype 抓的、能比文字更精确表达决策的片段可内联，标注"来自 prototype"。

何时用 / 不用

用 to-tickets

  • to-spec 后想正式开工
  • 活大到要跨多 session（spec 内的功能点多到一张 session 吃不下）
  • 想显式画依赖图，看清并行度
  • 想把多张 ticket 分给多个 agent（前端 / 后端 / schema）并行做

用 implement 而不是 to-tickets

  • spec 已经够小，单 session 内能做完
  • 不需要并行 / 不需要显式 DAG

用 prototype 而不是 to-tickets

  • 设计还没确定，先 throwaway code 验

用 wayfinder 而不是 to-tickets

  • 想法太大，连地图都没画出来
  • 先 wayfinder 解 decision tickets，结束后再 to-tickets 收口

不要用 to-tickets

  • 没有 spec 就想直接拆票 → 先回 to-spec 写 spec
  • bug 修复 → /triage → /diagnosing-bugs
  • 复杂度没大到需要 DAG → 直接 /implement
