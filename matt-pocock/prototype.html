prototype

throwaway code that answers a question——两个完全不同的 branch（LOGIC / UI），选错就全白干。用完扔，但作为 primary source 留下来。

用途

设计问题在纸上答不出来？跑一段代码让答案显形。prototype 不是"先写代码再说"——它是 throwaway code that answers a question。问题决定形状（LOGIC 或 UI），形状决定产物，产物决定怎么用。

两个核心不变量：

  • throwaway from day one——不是"先用着回头再扔"，而是一开始就标好是 prototype
  • 作为 primary source 留下来——commit 到 throwaway branch，main 只留验证过的决策

关键：prototype 不替代 spec。spec 是"做什么"，prototype 是验证某个具体决策的形状对不对。两者正交。

主流程位置

图 1 · prototype 作为 fork——主流程上任何"想跑一下看看"的地方都能塞进去

Fork 在哪儿出现？主流程任何一步都可能 detour 进 prototype。最常见的：

  • grill-with-docs 聊到某决策——"这状态机能在纸上推理吗？/ 这 UI 长什么样？"→ fork 到 prototype
  • 反过来 prototype 验证完 → 用 /handoff 把"判定 + 关键片段"带回主流程，再继续 to-spec / to-tickets

branch 选择（错了就全白干）

SKILL.md 自己说"the two branches produce very different artifacts, so getting this wrong wastes the whole prototype"。先问对问题：

问题 走 产物
"逻辑 / 状态感觉对吗？" LOGIC 单个 shareable HTML · 状态机 + 按钮 + 引导 walkthrough
"API 应该长什么样？" LOGIC 同上（纯逻辑 + 按钮驱动）
"这应该长什么样？" UI 同路由下 N 个变体 · ?variant= 切换 + 浮动 switcher

通用规则（两边都遵守）

  1. throwaway from day one, clearly marked——放在要用的模块旁边（context 清楚），命名一眼看出是 prototype；UI 路由按项目已有约定，不造新顶层结构
  2. trivial to run——UI prototype 一条命令（pnpm ）；logic demo 一个 HTML 双击开
  3. no persistence by default——state 在内存。"持久化"如果正是要验证的事，才上 scratch DB / 文件，命名带 "PROTOTYPE, wipe me"
  4. skip the polish——不写测试、不写错误处理（除非不写就跑不起来）、不抽象
  5. surface the state——LOGIC 每个 action 后打印完整状态；UI 每次切 variant 渲染
  6. capture as primary source——验证过的决策吸进真实代码；prototype 本身 commit 到 throwaway branch（不在 main），implementation issue 上留指针
第 6 条最重要：prototype 不扔。扔了就没法验证当时为什么这么决定；新人来也看不到当时的推理。Throwaway branch 是 prototype 的归宿。

# Prototype

A prototype is **throwaway code that answers a question**. The question
decides the shape.

## Pick a branch

- "Does this logic / state model feel right?" → LOGIC.md
- "What should this look like?" → UI.md

[两 branch 产物完全不同，选错就全白干。模糊时按上下文猜，顶部声明假设]

## Rules that apply to both

1. Throwaway from day one, clearly marked
2. Trivial to run
3. No persistence by default
4. Skip the polish
5. Surface the state
6. Capture as primary source — throwaway branch, primary source

SKILL.md 仅 27 行，是 dispatcher。真正的内容在 LOGIC.md（68 行）+ UI.md（113 行）。

LOGIC branch

LOGIC 单个 self-contained HTML 文件，让任何人通过点击按钮驱动一个状态模型。给非开发者也用得上——所以标签用人话而不是代码。

Anti-patterns

  • 写测试——需要测试的不是 prototype
  • 接真 DB——持久化如果是问题本身才接 scratch
  • "以后支持 X" 想太远——prototype 只答一个问题
  • 逻辑和页面混——模块一旦引用 DOM/document 就不 liftable
  • 用框架 / bundler / server——毁掉"shareable"
  • HTML 壳发到生产——壳是给手点优化的；模块才是要保留的

UI branch

UI 同一个路由下生成 N 个 结构不同 的变体，靠 URL search param 切换 + 浮动 switcher 切。

关键原则

UI prototype 必须嵌进真实 app 来评。孤立路由是真空——每个变体单独看都还行。Sub-shape A（默认）> Sub-shape B（最后手段）。

Sub-shape A · 改现有页面（默认）

路由已存在。变体渲染在同一个路由，按 ?variant= URL param 切换。已有 data fetch / params / auth 全保留，只换 subtree。

新东西也尽量嵌进 host page（dashboard 新区域、settings 新卡片、流程里新一步）——也是 sub-shape A。

Sub-shape B · 新建 throwaway 路由（最后手段）

只有当真没地方嵌（全新顶层 surface / 流程无法内嵌）才用。按项目路由约定走，命名带 prototype。同样用 ?variant= 模式。

N = 3（默认），cap 5

超过 5 个开始变成噪声，不是"radically different"。

变体必须 结构 不同

不同 layout / 不同信息层级 / 不同主交互——不是换颜色换文案。三个稍微微调的 card grid 不是 prototype，是 wallpaper。两个太像就重做一个，带"do not use a card grid"约束。

浮动 switcher bar

图 5 · 三个变体在同一页面下通过 URL 切换，浮动 switcher bar 永远在底部

Switcher bar 行为

  • 点击 ← / → 切换（循环）
  • 更新 URL search param（用框架 router：Next router.replace、React Router navigate）——可分享、可刷新
  • 键盘 ← / → 也能切——input / textarea / contenteditable 聚焦时不拦截
  • 视觉明显（高对比 pill + 阴影），不与被评估的页面混淆
  • 生产构建隐藏（process.env.NODE_ENV !== 'production'）——防漏到线上
  • 做成共享组件，两 sub-shape 复用

Anti-patterns

  • 变体只是颜色 / 文案不同——tweak，不是 prototype
  • 共享太多 layout（每个变体应能自由扔掉布局）
  • 接真 mutation——指向 stub，问的是"长什么样"，不是"后端行不行"
  • prototype 直接升生产——prototype 代码在 prototype 约束下写的，要重写

capture 流程

prototype 用完后，两件事要 capture：决策（折进真代码）+ prototype 本身（作为 primary source）。

图 6 · 决策进 main，prototype 整体进 throwaway branch，issue 留 verdict + 指针

两条 branch 的 capture 差异

LOGIC branch

  • 真模块（reducer / 状态机 / pure functions）lift 进真实模块——这是 决策
  • HTML 壳（page、按钮、walkthroughs）跟 prototype 一起进 throwaway branch

UI branch

Sub-shape决策（main）throwaway branch
A · 现有页面 winner 折进现有页面 loser + switcher + 全部变体
B · 新路由 winner 升为真路由 throwaway 路由 + switcher + 全部变体
Switcher 在 main 里会腐烂。变体组件 + switcher 留在 main 里会让下一个 reader 困惑（"这是要发的吗？"）——所以通通扔到 throwaway branch。

何时用 / 不用

用 prototype

  • 状态机 / 数据模型在纸上答不出来——"X 之后 Y 的边界情况对吗？"
  • UI 想看 3+ 个 radical options 才能挑
  • 不想花一天在脑里挑三个模糊的 mockup
  • 需要非开发者（PM、设计师、领域专家）按按钮体验

用 LOGIC 而不是 UI

  • 问题是逻辑 / 状态 / 数据形状 / API 形状
  • 答是 / 否 的事，不需要视觉对比

用 UI 而不是 LOGIC

  • 问题是"长什么样"
  • 要在多个 radical 选项里挑 / 拼

用 grill-with-docs 而不是 prototype

  • 问题是定义模糊、概念层面的（"我们到底要做什么"）——对话能搞定
  • 不需要看代码跑起来

用 to-spec 而不是 prototype

  • 想法已经清楚，不需要验证形状
  • 常规路径：spec → tickets → implement

不要用 prototype

  • 答案在对话里已经清楚——直接 spec
  • 只是修 bug——/triage → /diagnosing-bugs
  • 已经在动手写代码了——prototype 应该先于代码
  • 能直接进 grill-with-docs 解决的——对话便宜很多
