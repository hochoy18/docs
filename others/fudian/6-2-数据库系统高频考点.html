1 数据库基本概念

1.1 数据库核心定义

数据库（Database，简称 DB）是长期存储在计算机内、有组织、可共享的大量数据的集合。其核心特征是数据结构化、数据独立性高、冗余度低、可共享，能够满足多个用户或应用程序对数据的并发访问需求，同时保证数据的安全性和完整性。

数据库系统（Database System，简称 DBS）是由数据库、数据库管理系统、应用程序、数据库管理员（DBA）和用户组成的完整系统，其中数据库管理系统是核心组件，负责统一管理和控制数据库的访问。

数据库管理系统（Database Management System，简称 DBMS）是位于用户与操作系统之间的一层数据管理软件，主要功能包括数据定义、数据操纵、数据控制、数据库维护和数据通信，常见的 DBMS 有 MySQL、Oracle、SQL Server、PostgreSQL 等。

1.2 数据库的发展历程

•人工管理阶段（20 世纪 50 年代中期前）：无专门的数据库软件，数据由应用程序自行管理，数据与程序紧密绑定（数据独立性极差），数据不共享、冗余度极高，仅适用于单用户、小规模数据场景。

•文件系统阶段（20 世纪 50 年代中期-60 年代中期）：用操作系统的文件管理功能存储数据，数据以文件单位组织，实现了数据与程序的初步分离，但数据结构化程度低、共享性差、冗余度高，易出现数据不一致问题。

•数据库系统阶段（20 世纪 60 年代后期至今）：出现专门的 DBMS，数据采用结构化存储，具备高度共享性、低冗余度、高数据独立性，支持并发访问和数据安全控制，分为三个发展分支：

○层次数据库系统（如 IMS）：采用树形结构组织数据，适用于一对多的层级关系场景，灵活性差。

○网状数据库系统（如 CODASYL）：采用网状结构组织数据，支持多对多关系，结构复杂、维护困难。

○关系数据库系统：采用关系模型（二维表）组织数据，结构简单、易用、通用性强，是目前应用最广泛的数据库类型。

•新一代数据库阶段：随着大数据、人工智能的发展，出现 NoSQL 数据库（非关系型数据库）、NewSQL 数据库，NoSQL 数据库分为键值型、文档型、列族型、图型，适用于海量数据、高并发、弱结构化数据场景，弥补了传统关系数据库的不足。

1.3 数据库的核心特性

•数据结构化：数据按统一的结构（如关系模型的二维表）组织，数据之间的关联关系明确，不同于文件系统的松散组织。

•数据共享性高：多个用户、多个应用程序可同时访问数据库中的数据，避免了数据重复存储，提高了数据利用率。

•数据冗余度低：同一数据仅存储一次（或少量多次），通过关联关系实现数据复用，减少了数据冗余，降低了数据不一致的风险。

P3

•数据独立性高：分为物理独立性和逻辑独立性，是数据库系统与文件系统的核心区别：

○物理独立性：数据库的物理存储结构（如存储路径、存储方式）发生变化时，无需修改应用程序或数据的逻辑结构，仅需修改 DBMS 的配置。

○逻辑独立性：数据的逻辑结构（如表结构、字段关联）发生变化时，无需修改应用程序，仅需调整数据的逻辑映射关系。

•数据安全性：DBMS 提供完善的安全控制机制，可通过权限分配、加密、审计等方式，防止数据被非法访问、修改或泄露。

•数据完整性：保证数据库中的数据符合规定的约束条件，避免无效数据、错误数据的录入，分为实体完整性、参照完整性、用户定义完整性等。

•并发控制：支持多个用户同时操作数据库，通过锁机制、乐观并发控制等方式，避免并发操作导致的数据不一致（如脏读、不可重复读、幻读）。

•可恢复性：当数据库发生故障（如硬件故障、软件故障、人为误操作）时，DBMS 可通过备份和恢复机制，将数据恢复到故障前的正常状态。

1.4 数据库系统的组成

1.4.1 硬件平台

支撑数据库系统运行的硬件设备，需满足大容量存储、高运算速度、高可靠性的要求，包括服务器（数据库服务器、应用服务器）、存储设备（硬盘、磁盘阵列）、网络设备等，用于存储数据库文件和支撑并发访问。

1.4.2 软件系统

•数据库管理系统（DBMS）：核心软件，负责数据的定义、操纵、控制、维护和通信，是用户与数据库之间的接口。

•应用程序：由开发人员编写，通过 DBMS 提供的接口（如 SQL 语句、API）访问和操作数据库，满足具体的业务需求（如管理系统、查询系统）。

•操作系统（OS）：为 DBMS 和应用程序提供运行环境，负责管理硬件资源、进程调度、文件管理等，DBMS 需与操作系统兼容（如 MySQL 可运行在 Windows、Linux、Unix 等系统）。

•数据库驱动程序：实现应用程序与 DBMS 之间的通信，不同的 DBMS 对应不同的驱动程序（如 MySQL 的 JDBC 驱动、ODBC 驱动），用于解析应用程序的访问请求并传递给 DBMS。

1.4.3 人员

•数据库管理员（DBA）：负责数据库系统的整体管理和维护，核心职责包括数据库设计、权限分配、性能优化、备份恢复、故障处理、数据安全保障等，是数据库系统正常运行的关键角色。

•数据库设计人员：负责根据业务需求，设计数据库的逻辑结构和物理结构，包括表结构、字段定义、关联关系、索引设计等，确保数据结构合理、适配业务场景。

•应用程序开发人员：编写应用程序，通过 SQL 语句或 API 操作数据库，实现业务逻辑（如数据录入、查询、修改、删除），需熟悉 DBMS 的使用和数据结构。

P4

•最终用户：通过应用程序访问数据库，完成具体的业务操作（如查询数据、录入信息），无需了解数据库的底层实现和 SQL 语句。

1.5 数据库模型

数据库模型是对数据库中数据的结构、关联关系和操作规则的抽象描述，是数据库设计的基础，分为概念模型、逻辑模型和物理模型三类。

1.5.1 概念模型

又称信息模型，是对现实世界中数据关系的抽象描述，独立于具体的 DBMS 和硬件平台，用于梳理业务需求、搭建数据框架，常用的表示方法是实体-联系模型（E-R 模型）。

•核心概念：

○实体（Entity）：现实世界中可独立存在的客观事物或抽象概念，如学生、课程、员工，用矩形表示。

○属性（Attribute）：实体的特征，如学生的学号、姓名、年龄，用椭圆形表示，属性分为主键（唯一标识实体）、外键（关联其他实体）、普通属性。

○联系（Relationship）：实体之间的关联关系，用菱形表示，分为三类：

•一对一联系（1:1）：两个实体之间一一对应，如学生与学生证（一个学生对应一个学生证，一个学生证对应一个学生）。

•一对多联系（1:N）：一个实体可对应多个另一个实体，如班级与学生（一个班级有多个学生，一个学生属于一个班级）。

•多对多联系（M:N）：两个实体之间相互对应多个，如学生与课程（一个学生可选多门课程，一门课程可被多个学生选择），需通过中间表转换为一对多联系。

•E-R 模型的作用：梳理业务需求，明确实体、属性和联系，为后续逻辑模型设计（如关系表设计）提供依据，是数据库设计的核心步骤之一。

1.5.2 逻辑模型

是将概念模型转换为适配具体 DBMS 的数据结构，依赖于 DBMS 的类型，常用的逻辑模型包括：

•关系模型：用二维表（关系）表示数据和关联关系，表中的行称为元组（记录），列称为属性（字段），是目前应用最广泛的逻辑模型，适配关系型 DBMS（MySQL、Oracle）。

•层次模型：用树形结构表示数据，节点表示实体，边表示关联关系，仅支持一对多联系，适配层次型 DBMS。

•网状模型：用网状结构表示数据，节点表示实体，边表示关联关系，支持多对多联系，适配网状型 DBMS。

•NoSQL 模型：适配非关系型 DBMS，无固定结构，包括键值模型、文档模型、列族模型、图模型，用于存储弱结构化或半结构化数据。

1.5.3 物理模型

是对数据的物理存储结构和存储方式的描述，依赖于硬件平台和操作系统，包括数据的存储路径、存储格式、索引结构、分区方式等，由 DBA 和 DBMS 共同优化，目的是提升数据存储效率和访问速度。

2 关系数据库理论与 SQL

2.1 关系数据库核心理论

2.1.1 关系模型的基本概念

关系模型是关系数据库的基础，核心是用“关系”（二维表）描述数据，所有数据都存储在表中，表与表之间通过关联关系（外键）实现数据共享和联动。

•关系（Relation）：即二维表，是具有相同结构的元组的集合，每个关系有唯一的名称（表名），关系需满足原子性（每个字段的值不可再拆分）、无重复元组（无重复记录）、无行序（行的顺序不影响数据含义）、无列序（列的顺序不影响数据含义）。

•元组（Tuple）：关系中的一行，对应一条具体的记录（如一个学生的信息），每个元组的结构与关系的属性结构一致。

•属性（Attribute）：关系中的一列，对应实体的一个特征（如学号、姓名），每个属性有唯一的名称（字段名），并定义了数据类型（如 int、varchar、date）和约束条件（如非空、唯一）。

•域（Domain）：属性的取值范围，即一个属性可能取到的所有合法值，如性别属性的域为｛男，女｝，年龄属性的域为大于 0 且小于 150 的整数。

•关键字（Key）：用于唯一标识关系中的元组，分为以下几类：

○候选码（Candidate Key）：一组属性的集合，能够唯一标识元组，且去掉集合中的任意一个属性后，无法再唯一标识元组（最小性），一个关系可能有多个候选码。

○主码（Primary Key，简称主键）：从多个候选码中选择一个作为唯一标识元组的关键字，每个关系有且仅有一个主键，主键属性的值不可为空、不可重复。

○外码（Foreign Key，简称外键）：一个关系中的一组属性，其取值对应另一个关系的主键值，用于建立两个关系之间的关联关系，外键可以为空，也可以重复。

○主属性与非主属性：候选码中的属性称为主属性，非候选码中的属性称为非主属性。

•关系模式：对关系的结构描述，格式为：关系名（属性 1，属性 2，⋯，属性 n，主键，外键），如学生表的关系模式为：学生（学号，姓名，性别，年龄，班级号，主键：学号，外键：班级号）。

2.1.2 关系的完整性约束

关系的完整性约束是为了保证关系中的数据合法、有效、一致，是关系数据库的核心特性之一，分三类：

•实体完整性：核心是保证主键的唯一性和非空性，即关系中的每个元组必须通过主键唯一标识，主键属性的值不能为 null，也不能重复。例如，学生表中，学号作为主键，不能有两个学生的学号相同，也不能有学生的学号为空。

P6

•参照完整性：又称引用完整性，用于维护两个关系之间的关联关系（通过外键），核心规则是：外键的值必须要么为空，要么等于被引用关系（主表）中对应的主键值，不能引用主表中不存在的主键值。例如，学生表的班级号是外键，引用班级表的班级号（主键），则学生表的班级号只能是班级表中已存在的班级号，或为空。

•用户定义完整性：根据具体的业务需求，自定义的约束条件，用于限制属性的取值范围或格式，常见的有非空约束、唯一约束、检查约束、默认值约束等。例如，性别属性只能取“男”或“女”，年龄属性必须大于 0 且小于 150，邮箱属性必须符合邮箱格式。

2.1.3 关系代数

关系代数是一种基于关系的运算体系，用于对关系（表）进行查询、筛选、组合等操作，运算结果仍然是一个关系，是 SQL 查询语句的理论基础，分为传统集合运算和专门关系运算。

2.1.3.1 传统集合运算

基于集合的基本运算，要求两个操作关系的结构完全一致（属性个数、属性类型、属性顺序相同），包括：

•并运算（∪）：将两个关系中的元组合并，去掉重复元组，得到一个新关系，新关系的元组是两个原关系元组的合集。例如，关系 A 和关系 B 合并后，包含 A 和 B 中所有不重复的记录。

•交运算（∩）：取两个关系中共同的元组（同时存在于两个关系中的元组），得到一个新关系。例如，关系 A 和关系 B 的交运算结果，是既在 A 中又在 B 中的记录。

•差运算（-）：取属于第一个关系但不属于第二个关系的元组，得到一个新关系，注意运算顺序不可颠倒（A-B 与 B-A 结果不同）。例如，A-B 的结果是在 A 中但不在 B 中的记录。

•笛卡尔积（×）：将两个关系中的元组进行所有可能的组合，新关系的属性个数是两个原关系属性个数之和，元组个数是两个原关系元组个数之积，笛卡尔积的结果通常需要进一步筛选（结合选择运算）。

2.1.3.2 专门关系运算

针对关系的特性设计的运算，无需两个关系结构一致，是关系查询的核心运算，包括：

•选择运算（σ）：从一个关系中筛选出满足指定条件的元组，保留原关系的属性结构，相当于 SQL 中的 WHERE 子句。例如，从学生表中筛选出年龄大于 18 的学生记录，条件为 σ（学生）。

•投影运算（π）：从一个关系中选择指定的属性列，去掉重复元组，得到一个新关系，相当于 SQL 中的 SELECT 子句（指定字段）。例如，从学生表中选择学号、姓名、年龄三个属性，表达式为 π（学生）。

•连接运算（∞）：将两个关系通过指定的条件（通常是属性之间的相等条件）进行组合，筛选出满足条件的元组，是笛卡尔积的优化运算，分为内连接、外连接、交叉连接等：

○内连接（等值连接）：仅保留两个关系中满足连接条件的元组，是最常用的连接方式，例如，将学生表和班级表通过班级号连接，仅保留有对应班级的学生记录。

P7

○外连接：分为左外连接、右外连接、全外连接，保留一个或两个关系中不满足连接条件的元组，未匹配的属性值设为 null：

•左外连接：保留左关系的所有元组，右关系中不满足连接条件的元组设为 null。

•右外连接：保留右关系的所有元组，左关系中不满足连接条件的元组设为 null。

•全外连接：保留两个关系的所有元组，不满足连接条件的元组对应的属性值设为 null。

○交叉连接：等价于笛卡尔积，无连接条件，保留所有可能的元组组合。

•除法运算（÷）：用于解决“查询满足所有条件的元组”的问题，运算逻辑复杂，需先确定除数关系的属性集，再从被除数关系中筛选出包含除数所有元组对应的属性值的元组，例如，查询选修了所有课程的学生记录。

2.1.4 规范化理论（范式）

规范化理论的核心是解决关系模式中的数据冗余、插入异常、删除异常、更新异常等问题，通过对关系模式进行分解，使其满足不同级别的范式（Normal Form，简称 NF），常用的范式有第一范式（1NF）、第二范式（2NF）、第三范式（3NF），更高阶的范式有 BCNF、4NF、5NF，范式级别越高，关系模式越合理，数据冗余越少。

2.1.4.1 常见异常问题

•数据冗余：同一数据重复存储，例如，一个课程被多个学生选修，课程名称、授课老师等信息会随每个学生记录重复存储，浪费存储空间。

•插入异常：无法插入某些合法数据，例如，若关系模式为“学生选课（学号，姓名，课程号，课程名，成绩）”，当新增一门课程但暂无学生选课时，由于学号（主键之一）为空，无法插入课程信息。

•删除异常：删除某些数据时，会误删其他相关数据，例如，删除某学生的选课记录时，会同时删除该课程的名称、授课老师等信息，导致课程信息丢失。

•更新异常：修改某一数据时，需修改多个相关元组，易导致数据不一致，例如，修改一门课程的名称时，需修改所有选修该课程的学生记录中的课程名称，若遗漏则会出现数据不一致。

2.1.4.2 各范式定义

•第一范式（1NF）：最基础的范式，要求关系中的每个属性都是原子值（不可再拆分），无复合属性、多值属性。例如，“地址”属性若包含省、市、区，则不满足 1NF，需拆分为省、市、区三个独立属性。所有关系模式都必须满足 1NF，否则无法成为关系数据库。

•第二范式（2NF）：在满足 1NF 的基础上，要求关系中的每一个非主属性完全函数依赖于主键，消除部分函数依赖（非主属性仅依赖于主键的一部分）。适用场景：主键为复合主键（多个属性组成的主键），例如，将“学生选课”关系模式拆分为“学生（学号，姓名）”“课程（课程号，课程名）”“选课（学号，课程号，成绩）”，选课表的主键为（学号，课程号），成绩完全依赖于主键，满足 2NF。

•第三范式（3NF）：在满足 2NF 的基础上，要求关系中的每一个非主属性既不传递依赖于主键，也不依赖于其他非主属性，消除传递函数依赖（非主属性依赖于主键，且依赖于另一个非主属性）。例如，“学生（学号，姓名，班级号，班级名称）”中，班级名称依赖于班级号，班级号依赖于学号，属于传递依赖，需拆分为“学生（学号，姓名，班级号）”“班级（班级号，班级名称）”，拆分后两个关系均满足 3NF。

P8

•BCNF 范式：在满足 3NF 的基础上，要求关系中的每一个函数依赖的左部都是候选码，消除主属性对候选码的部分依赖和传递依赖，是实际应用中常用的最高阶范式，适用于对数据一致性要求极高的场景。

2.1.4.3 规范化原则

规范化的核心是“分解关系模式”，分解时需遵循两个原则：无损连接性（分解后的关系通过连接运算可还原为原关系，无数据丢失）和函数依赖保持性（分解后的关系保留原关系的所有函数依赖，无依赖丢失），优先保证无损连接性，再考虑函数依赖保持性。

2.2 SQL 基础与核心语法

SQL （Structured Query Language，结构化查询语言）是用于操作关系型数据库的标准语言，适用于所有关系型 DBMS，具有统一的语法规范，分为数据定义语言（DDL）、数据操纵语言（DML）、数据查询语言（DQL）、数据控制语言（DCL）四类。

2.2.1 SQL 基本规则

•SQL 语句不区分大小写（关键字、表名、字段名均可大小写混用），但建议关键字大写，表名、字段名小写，提高可读性。

•每条 SQL 语句以分号（；）结束，若为单条语句，部分 DBMS（如 MySQL）可省略分号，但建议统一添加。

•注释：单行注释用--（两个减号）开头，多行注释用/*注释内容 */包裹，注释内容不会被 DBMS 执行。

•字段名、表名若包含特殊字符（如空格、中文），需用反引号（`）包裹（MySQL）或方括号（[]）包裹（SQL Server）。

2.2.2 数据定义语言（DDL）

用于定义数据库、表、索引、视图等数据库对象的结构，核心操作包括创建、修改、删除，执行后会永久生效，无需提交事务。

2.2.2.1 数据库操作

•创建数据库：

CREATE DATABASE [IF NOT EXISTS] 数据库名 [DEFAULT CHARACTER SET 字符集] [DEFAULT COLLATE 排序规则];
-- 示例：创建名为 student_db 的数据库，字符集为 utf8mb4，支持中文和特殊字符
CREATE DATABASE IF NOT EXISTS student_db DEFAULT CHARACTER SET utf8mb4 DEFAULT COLLATE utf8mb4_general_ci;

ALTER DATABASE 数据库名 DEFAULT CHARACTER SET 新字符集 DEFAULT COLLATE 新排序规则;
-- 示例：修改 student_db 的字符集为 utf8
ALTER DATABASE student_db DEFAULT CHARACTER SET utf8 DEFAULT COLLATE utf8_general_ci;

•删除数据库：删除数据库及其所有内容（表、数据、索引等），操作不可逆，需谨慎。

-- 示例：删除 student_db 数据库
DROP DATABASE IF EXISTS student_db;

USE 数据库名;

•创建表：

CREATE TABLE [IF NOT EXISTS] 表名 (

字段名 2 数据类型 [约束条件],

[主键约束],
[外键约束],
[唯一约束]
)[ENGINE=存储引擎][DEFAULT CHARSET=字符集];
-- 示例：创建学生表 student，主键为学号，外键班级号关联班级表
CREATE TABLE IF NOT EXISTS student (

2.2.2.3 索引操作

索引是用于提升查询效率的数据库对象，通过索引可快速定位数据，减少表扫描的次数，适用于查询频繁、数据量大的表，索引会占用额外存储空间，且插入、修改、删除数据时会维护索引，降低写入效率，需合理设计。

-- 示例：给 student 表的 sname 字段创建普通索引
CREATE INDEX idx_stu_sname ON student (sname);
-- 示例：给 student 表的 email 字段创建唯一索引
CREATE UNIQUE INDEX idx_stu_email ON student (email);

2.2.3 数据操纵语言（DML）

用于对表中的数据进行插入、修改、删除操作，执行后需提交事务（COMMIT）才能永久生效，可通过回滚（ROLLBACK）撤销未提交的操作，适用于 InnoDB 存储引擎（支持事务），MyISAM 不支持事务。

2.2.3.1 插入数据（INSERT）

•插入单条数据：

INSERT INTO 表名 (字段名 1, 字段名 2, ...) VALUES (值 1, 值 2, ...);
-- 示例：给 student 表插入一条学生数据
INSERT INTO student (sid, sname, gender, age, cid) VALUES (1001, '张三', '男', 20, 101);

•插入多条数据：

INSERT INTO 表名 (字段名 1, 字段名 2, ...) VALUES (值 1, 值 2, ...), (值 1, 值 2, ...);
-- 示例：给 student 表插入多条学生数据
INSERT INTO student (sid, sname, gender, age, cid)
VALUES (1002, '李四', '女', 19, 101), (1003, '王五', '男', 21, 102);

•插入查询结果：将一个查询的结果插入到表中，要求查询结果的字段个数、数据类型与目标表匹配。

INSERT INTO 目标表名 (字段名 1, 字段名 2) SELECT 字段名 1, 字段名 2 FROM 源表名 [WHERE 条件];
-- 示例：将 student 表中班级号为 101 的学生插入到 stu_101 表中
INSERT INTO stu_101 (sid, sname, gender, age, cid)
SELECT sid, sname, gender, age, cid FROM student WHERE cid = 101;

•注意事项：字段值需与字段的数据类型匹配；主键、非空约束字段必须赋值：唯一约束字段的值不可重复；日期类型的值需用引号包裹（如'2024-01-01'）。

2.2.3.2 修改数据（UPDATE）

SQL
UPDATE 表名 SET 字段名 1 = 值 1, 字段名 2 = 值 2 [WHERE 条件];
-- 示例：将 student 表中学号为 1001 的学生年龄改为 21
UPDATE student SET age = 21 WHERE sid = 1001;
-- 示例：将班级号为 101 的学生性别改为女（谨慎使用，无 WHERE 条件会修改所有数据）

注意事项：WHERE 子句用于指定修改的范围，若省略 WHERE 子句，会修改表中的所有数据，需格外谨慎；修改外键字段时，需保证修改后的值在主表的主键中存在，符合参照完整性；修改主键字段时，需保证新值唯一、非空。

2.2.3.3 删除数据（DELETE）

SQL
DELETE FROM 表名 [WHERE 条件];
-- 示例：删除 student 表中学号为 1003 的学生数据
DELETE FROM student WHERE sid = 1003;
-- 示例：删除班级号 102 的所有学生数据
DELETE FROM student WHERE cid = 102;

•注意事项：省略 WHERE 子句会删除表中的所有数据（表结构保留），操作不可逆，需谨慎；删除有外键关联的子表数据时，若主表数据被引用，需先删除子表数据，再删除主表数据（或设置外键级联删除）；DELETE 删除数据后，自增字段的计数器不会重置，若需重置，可使用 TRUNCATE。

•TRUNCATE 与 DELETE 的区别：

○DELETE：删除表中的数据，保留表结构，支持 WHERE 条件，可回滚，不重置自增计数器，删除速度较慢（需逐行删除并记录日志）。

○TRUNCATE：删除表中的所有数据，保留表结构，不支持 WHERE 条件，不可回滚，重置自增计数器，删除速度较快（直接清空表，不记录日志），有外键关联的表无法使用 TRUNCATE。

TRUNCATE TABLE 表名;
-- 示例：清空 student 表的所有数据
TRUNCATE TABLE student;

SELECT DISTINCT cid FROM student;

-- 5. 聚合函数查询（统计数据）
-- 常用聚合函数：COUNT(字段)（统计记录数）、SUM(字段)（求和）、AVG(字段)（求平均）、MAX(字段)（求最大值）、MIN(字段)（求最小值）
SELECT 聚合函数(字段名) AS 别名 FROM 表名 [WHERE 条件];
-- 示例：统计 student 表中的学生总数
SELECT COUNT(*) AS 学生总数 FROM student;
-- 示例：统计班级号为 101 的学生平均年龄
SELECT AVG(age) AS 平均年龄 FROM student WHERE cid = 101;

2.2.4.2 条件查询（WHERE 子句）

用于筛选满足条件的记录，支持多种条件运算符，可组合使用。

•比较运算符：=（等于）、!=/<>（不等于）、>（大于）、<（小于）、>=（大于等于）、<=（小于等于）、BETWEEN … AND …（在某个范围之间，包含边界）、IN（在指定集合中）、NOT IN（不在指定集合中）、IS NULL（为空）、IS NOT NULL（不为空）。

-- 示例：查询年龄大于 19 且小于等于 21 的学生
SELECT * FROM student WHERE age > 19 AND age <= 21;
-- 示例：查询年龄在 18-22 之间的学生（等价于 age >=18 AND age <=22）
SELECT * FROM student WHERE age BETWEEN 18 AND 22;
-- 示例：查询班级号为 101 或 102 的学生
SELECT * FROM student WHERE cid IN (101, 102);
-- 示例：查询邮箱空的学生
SELECT * FROM student WHERE email IS NULL;
P14

•逻辑运算符：AND（逻辑与，多个条件同时满足）、OR（逻辑或，多个条件满足一个即可）、NOT（逻辑非，取反条件）。

-- 示例：查询班级号为 101、性别为女且年龄大于 19 的学生
SELECT * FROM student WHERE cid = 101 AND gender = '女' AND age > 19;
-- 示例：查询性别为男或年龄大于 20 的学生
SELECT * FROM student WHERE gender = '男' OR age > 20;

•模糊查询（LIKE）：用于匹配字符串类型的字段，支持通配符：%（匹配任意个字符，包括 0 个）、_（匹配单个字符）。

-- 示例：查询姓名以“张”开头的学生
SELECT * FROM student WHERE sname LIKE '张%';
-- 示例：查询姓名中间包含“四”的学生
SELECT * FROM student WHERE sname LIKE '%四%';
-- 示例：查询姓名长度为 3，且以“李”开头的学生（_匹配单个字符）
SELECT * FROM student WHERE sname LIKE '李_';

2.2.4.3 排序查询（ORDER BY 子句）

用于对查询结果按指定字段排序，默认升序（ASC），可指定降序（DESC），支持多字段排序。

SQL
SELECT 字段名 FROM 表名 [WHERE 条件] ORDER BY 字段名 1 [ASC/DESC], 字段名 2 [ASC/DESC];
-- 示例：查询 student 表中的学生，按年龄降序排序（年龄大的在前）
SELECT * FROM student ORDER BY age DESC;
-- 示例：按班级号升序、年龄降序排序，同一班级内年龄大的在前
SELECT * FROM student ORDER BY cid ASC, age DESC;

2.2.4.4 分组查询（GROUP BY 子句）

用于将查询结果按指定字段分组，每组统计一次数据（结合聚合函数），分组后的数据仅能查询分组字段和聚合函数结果，HAVING 子句用于筛选分组后的结果（区别于 WHERE: WHERE 筛选行，HAVING 筛选分组）。

SQL
SELECT 分组字段, 聚合函数(字段名) AS 别名 FROM 表名 [WHERE 条件] GROUP BY 分组字段 [HAVING 分组条件];
-- 示例：按班级号分组，统计每个班级的学生人数
SELECT cid 班级号, COUNT(*) 学生人数 FROM student GROUP BY cid;
-- 示例：按班级号分组，统计每个班级的平均年龄，筛选平均年龄大于 20 的班级
SELECT cid 班级号, AVG(age) 平均年龄 FROM student GROUP BY cid HAVING AVG(age) > 20;
P15

2.2.4.5 限制查询结果（LIMIT 子句）

用于限制查询结果的条数，适用于分页查询，仅 MySQL 支持，SQL Server 用 TOP, Oracle 用 ROWNUM。

SQL
-- 格式 1：LIMIT 条数（查询前 n 条记录）
SELECT * FROM 表名 LIMIT n;
-- 示例：查询 student 表中的前 3 条记录
SELECT * FROM student LIMIT 3;

-- 格式 2：LIMIT 偏移量，条数（分页查询，偏移量从 0 开始）
SELECT * FROM 表名 LIMIT (页码-1) * 每页条数, 每页条数;
-- 示例：分页查询，每页 2 条，查询第 2 页（偏移量 2，查询第 3、4 条）
SELECT * FROM student LIMIT 2,2;

2.2.4.6 多表连接查询

用于查询多个表中的关联数据，核心是通过外键建立连接条件，分为内连接、外连接、交叉连接，与关系代数的连接运算对应。

SQL
-- 1. 内连接（INNER JOIN，可省略 INNER）
SELECT 字段名 FROM 表 1 INNER JOIN 表 2 ON 表 1.外键字段 = 表 2.主键字段 [WHERE 条件];
-- 示例：查询学生姓名和对应的班级名称（student 表和 class 表连接）
SELECT s.sname 学生姓名, c.cname 班级名称
FROM student s INNER JOIN class c
ON s.cid = c.cid;

-- 2. 左外连接（LEFT JOIN/LEFT OUTER JOIN, OUTER 可省略）
SELECT 字段名 FROM 表 1 LEFT JOIN 表 2 ON 表 1.外键字段 = 表 2.主键字段 [WHERE 条件];
-- 示例：查询所有学生及对应班级名称，无对应班级的学生显示为 null
SELECT s.sname 学生姓名, c.cname 班级名称
FROM student s LEFT JOIN class c
ON s.cid = c.cid;

-- 3. 右外连接（RIGHT JOIN/RIGHT OUTER JOIN, OUTER 可省略）
SELECT 字段名 FROM 表 1 RIGHT JOIN 表 2 ON 表 1.外键字段 = 表 2.主键字段 [WHERE 条件];
-- 示例：查询所有班级及对应学生姓名，无学生的班级显示为 null
SELECT s.sname 学生姓名, c.cname 班级名称
FROM student s RIGHT JOIN class c
ON s.cid = c.cid;
P16
-- 4. 全外连接（FULL JOIN/FULL OUTER JOIN）
-- 注意：MySQL 不直接支持 FULL JOIN，需用 LEFT JOIN + UNION + RIGHT JOIN 实现
SELECT 字段名 FROM 表 1 LEFT JOIN 表 2 ON 表 1.外键字段 = 表 2.主键字段
UNION
SELECT 字段名 FROM 表 1 RIGHT JOIN 表 2 ON 表 1.外键字段 = 表 2.主键字段;
-- 示例：查询所有学生和所有班级的对应关系，双方无匹配的均显示为 null
SELECT s.sname 学生姓名, c.cname 班级名称
FROM student s LEFT JOIN class c ON s.cid = c.cid
UNION
SELECT s.sname 学生姓名, c.cname 班级名称
FROM student s RIGHT JOIN class c ON s.cid = c.cid;

-- 5. 交叉连接（CROSS JOIN），等价于笛卡尔积，无连接条件
SELECT 字段名 FROM 表 1 CROSS JOIN 表 2 [WHERE 条件];
-- 示例：查询学生和班级的所有组合（无实际业务意义，仅作演示）
SELECT s.sname 学生姓名, c.cname 班级名称
FROM student s CROSS JOIN class C;

2.2.4.7 子查询

子查询（又称嵌套查询）是将一个 SELECT 语句嵌套在另一个 SQL 语句（SELECT、INSERT、UPDATE、DELETE）中，内层查询的结果作为外层查询的条件或数据源。子查询需用括号包裹，根据返回结果的条数，分为单行子查询、多行子查询、多列子查询。

2.2.4.7.1 单行子查询

内层查询返回一条记录，适用于搭配单行比较运算符（=、>、<、>=、<=、!=）使用。

SQL
-- 示例 1：查询与“张三”同龄的学生
SELECT sname, age FROM student
WHERE age = (SELECT age FROM student WHERE sname = '张三');

-- 示例 2：查询年龄大于平均年龄的学生
SELECT sname, age FROM student
WHERE age > (SELECT AVG(age) FROM student);
P17
2.2.4.7.2 多行子查询

内层查询返回多条记录，需搭配多行运算符（IN、NOT IN、ANY、ALL）使用。

SQL
-- 示例 1：查询选修了“数据库”课程的学生姓名（需关联选课表、课程表、学生表）
SELECT sname FROM student
WHERE sid IN (SELECT sid FROM sc WHERE cid = (SELECT cid FROM course WHERE cname = '数据库'));

-- 示例 2：查询年龄大于班级号为 101 的所有学生年龄的学生
SELECT sname, age FROM student
WHERE age > ALL (SELECT age FROM student WHERE cid = 101);

-- 示例 3：查询年龄大于班级号 101 的任意一个学生年龄的学生
SELECT sname, age FROM student
WHERE age > ANY (SELECT age FROM student WHERE cid = 101);
2.2.4.7.3 多列子查询

内层查询返回多列数据，适用于外层查询需匹配多个字段的场景，常用 IN、EXISTS 搭配。

SQL
-- 示例：查询与“张三”同班级、同性别且同龄的学生
SELECT sname, cid, gender, age FROM student
WHERE (cid, gender, age) IN (SELECT cid, gender, age FROM student WHERE sname = '张三')
AND sname != '张三';
2.2.4.7.4 EXISTS 与 NOT EXISTS 子查询

用于判断内层查询是否返回结果，存在则返回 true，不存在则返回 false，仅关注“是否存在”，不关注具体数据，效率通常高于 IN 子查询（尤其数据量大时）。

SQL
-- 示例 1：查询存在选课记录的学生姓名
SELECT sname FROM student s
WHERE EXISTS (SELECT * FROM sc WHERE sc.sid = s.sid);

-- 示例 2：查询无选课记录的学生姓名
SELECT sname FROM student s
WHERE NOT EXISTS (SELECT * FROM sc WHERE sc.sid = s.sid);
P18

2.2.4.8 合并查询结果（UNION 与 UNION ALL）

用于合并多个 SELECT 语句的查询结果，要求多个查询的字段个数、数据类型、字段顺序一致，区别在于是否去重。

SQL
-- 1.UNION：合并结果并去重，效率较低（需比对重复数据）
SELECT sname, age FROM student WHERE cid = 101
UNION
SELECT sname, age FROM student WHERE cid = 102;

-- 2. UNION ALL：合并结果但不去重，效率较高，适用于无需去重的场景
SELECT sname, age FROM student WHERE cid = 101
UNION ALL
SELECT sname, age FROM student WHERE cid = 102;

注意：UNION 和 UNION ALL 仅能合并查询结果，不能合并其他 SQL 语句（如 UPDATE、DELETE），且合并时字段的含义需一致。

2.2.5 数据控制语言（DCL）

用于控制数据库的访问权限，核心操作是授权和回收权限，仅 DBA 或拥有对应权限的用户可执行，执行后永久生效。

2.2.5.1 授权（GRANT）

给用户分配指定的数据库操作权限，权限可细化到数据库、表、字段，常用权限包括 SELECT（查询）、INSERT（插入）、UPDATE（修改）、DELETE（删除）、CREATE（创建）、DROP（删除）、ALL PRIVILEGES（所有权限）。

SQL
-- 基本语法：GRANT 权限列表 ON 数据库.表名 TO '用户名'@'登录地址' [IDENTIFIED BY'密码'];
-- 1. 给用户分配指定数据库所有表的查询和插入权限
GRANT SELECT, INSERT ON student_db.* TO 'user1'@localhost IDENTIFIED BY '123456';

-- 2. 给用户分配指定表的所有权限
GRANT ALL PRIVILEGES ON student_db.student TO 'user2'@'%' IDENTIFIED BY '654321';
-- 说明：%表示允许该用户从任意地址登录，localhost 表示仅允许本地登录
P19
-- 3. 给用户分配权限并允许其授权给其他用户（添加 WITH GRANT OPTION）
GRANT SELECT ON student_db.course TO 'user3'@'localhost' IDENTIFIED BY '111222' WITH GRANT OPTION;

2.2.5.2 回收权限（REVOKE）

收回用户已有的权限，语法与授权对应，需注意：收回权限后，用户若已授权给其他用户，需同步收回被授权用户的对应权限。

SQL
-- 基本语法：REVOKE 权限列表 ON 数据库.表名 FROM '用户名'@'登录地址';
-- 1. 收回用户指定数据库所有表的插入权限
REVOKE INSERT ON student_db.* FROM 'user1'@'localhost';

-- 2. 收回用户指定表的所有权限
REVOKE ALL PRIVILEGES ON student_db.student FROM 'user2'@'%';

2.2.5.3 管理用户（创建、删除、修改密码）

SQL
-- 1. 创建用户
CREATE USER '用户名'@'登录地址' IDENTIFIED BY '密码';
-- 示例：创建本地用户 user4，密码为 123abc
CREATE USER 'user4'@'localhost' IDENTIFIED BY '123abc';

-- 2. 删除用户
DROP USER '用户名'@登录地址;
-- 示例：删除用户 user4
DROP USER 'user4'@'localhost';

-- 3. 修改用户密码（MySQL 8.0+语法）
ALTER USER '用户名'@'登录地址' IDENTIFIED BY '新密码';
-- 示例：修改 user1 的密码为 666abc
ALTER USER 'user1'@'localhost' IDENTIFIED BY '666abc';

2.2.6 事务控制语言（TCL）

事务（Transaction）是一组不可分割的 SQL 操作集合，要么全部执行成功，要么全部执行失败（原子性），适用于 InnoDB 存储引擎，MyISAM 不支持事务。TCL 用于控制事务的提交、回滚，核心语句包括 COMMIT、ROLLBACK、SAVEPOINT。

P20

2.2.6.1 事务的 ACID 特性

•原子性（Atomicity）：事务中的所有操作要么全部执行，要么全部回滚，无部分执行的情况，例如转账时，扣款和到账操作必须同时成功或同时失败。

•一致性（Consistency）：事务执行前后，数据库的数据完整性约束不被破坏，例如转账前后，两个账户的总金额保持不变。

•隔离性（Isolation）：多个事务并发执行时，一个事务的操作不会影响另一个事务的执行，避免并发问题（脏读、不可重复读、幻读），数据库通过隔离级别控制隔离性。

•持久性（Durability）：事务提交后，数据的修改会永久保存到数据库中，即使发生硬件故障或软件故障，数据也不会丢失。

2.2.6.2 事务控制语句

SQL
-- 1. 开启事务（默认自动提交关闭，需手动开启）
START TRANSACTION; -- 或 BEGIN;

-- 2. 提交事务（将事务中的操作永久保存到数据库）
COMMIT;

-- 3. 回滚事务（撤销事务中的所有操作，回到事务开启前的状态）
ROLLBACK;

-- 4. 设置保存点（在事务中设置断点，可回滚到指定保存点，不影响保存点之前的操作）
SAVEPOINT 保存点名称;
-- 回滚到指定保存点
ROLLBACK TO 保存点名称;
-- 删除保存点
RELEASE SAVEPOINT 保存点名称;

-- 示例：模拟转账事务
START TRANSACTION;
-- 账户 A 扣款 100
UPDATE account SET balance = balance - 100 WHERE account_id = 'A';
-- 账户 B 到账 100
UPDATE account SET balance = balance + 100 WHERE account_id = 'B';
-- 若执行无异常，提交事务
COMMIT;
-- 若执行有异常，回滚事务
-- ROLLBACK;
P21

2.2.6.3 事务隔离级别

数据库通过设置隔离级别，解决并发事务带来的问题，MySQL 默认隔离级别 REPEATABLE READ（可重复读），不同隔离级别对应不同的并发问题解决方案。

隔离级别脏读不可重复读幻读说明
读未提交（READ UNCOMMITTED）允许允许允许最低隔离级别，一个事务可读取另一个未提交事务的修改，易导致数据不一致
读已提交（READ COMMITTED）禁止允许允许一个事务仅能读取另一个已提交事务的修改，避免脏读，Oracle 默认隔离级别
可重复读（REPEATABLE READ）禁止禁止允许MySQL 默认隔离级别，保证同一事务中多次读取同一数据结果一致，避免不可重复读
串行化（SERIALIZABLE）禁止禁止禁止最高隔离级别，事务串行执行，无并发问题，但性能极低，适用于数据一致性要求极高的场景

隔离级别设置语法：

SQL
-- 查看当前会话隔离级别
SELECT @@session.tx_isolation;
-- 设置当前会话隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL 隔离级别名称;
-- 示例：设置为读已提交
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 查看全局隔离级别
SELECT @@global.tx_isolation;
-- 设置全局隔离级别（需重启会话生效）
SET GLOBAL TRANSACTION ISOLATION LEVEL 隔离级别名称;

2.2.7 视图（View）

视图是基于一个或多个表的查询结果构建的虚拟表，不存储实际数据，仅存储查询语句，数据来源于底层的基表，当基表数据发生变化时，视图数据也会同步更新。视图的核心作用是简化查询、隐藏数据细节、控制数据访问权限。

2.2.7.1 视图的创建

SQL
CREATE VIEW [IF NOT EXISTS] 视图名 AS SELECT 语句 [WITH CHECK OPTION];
-- WITH CHECK OPTION：确保通过视图插入、修改的数据符合视图的查询条件，避免插入/修改的数据无法通过视图查询到
-- 示例：创建视图，查询 101 班级的学生信息
CREATE VIEW V_stu_101 AS
SELECT sid, sname, gender, age FROM student WHERE cid = 101 WITH CHECK OPTION;

2.2.7.2 视图的查询

视图的查询与普通表一致，直接使用 SELECT 语句查询即可。

SQL
-- 示例：查询视图 v_stu_101 中的学生信息
SELECT * FROM v_stu_101;

2.2.7.3 视图的修改

SQL
-- 方式 1：CREATE OR REPLACE VIEW（覆盖原有视图）
CREATE OR REPLACE VIEW V_stu_101 AS
SELECT sid, sname, age FROM student WHERE cid = 101;

-- 方式 2：ALTER VIEW
ALTER VIEW v_stu_101 AS
SELECT sid, sname, gender FROM student WHERE cid = 101;
P23

2.2.7.4 视图的删除

SQL
DROP VIEW [IF EXISTS] 视图名;
-- 示例：删除视图 v_stu_101
DROP VIEW IF EXISTS v_stu_101;

2.2.7.5 视图的注意事项

•视图不存储数据，仅存储查询语句，查询视图本质是执行底层的 SELECT 语句。

•并非所有视图都支持插入、修改、删除操作，若视图包含聚合函数、DISTINCT、GROUP BY、UNION 等，无法执行 DML 操作。

•WITH CHECK OPTION 仅对通过视图执行的 DML 操作生效，直接操作基表不受限制。

3 数据库对象与完整性

3.1 核心数据库对象

数据库对象是数据库中存储、管理数据的各类结构的统称，由 DBMS 创建和维护，核心对象包括表、索引、视图、存储过程、触发器、序列等，各类对象协同工作，支撑数据库的高效运行和数据管理。

3.1.1 表（Table）

表是数据库中最基础、最核心的对象，是存储数据的二维结构，由行（元组/记录）和列（属性/字段）组成，用于结构化存储实际业务数据，是所有数据库操作的基础。

•核心特性：每个表有唯一名称，字段需定义数据类型和约束条件；行具有原子性（每行对应一条完整记录），列具有同质性（每列数据类型一致）；表中的数据需遵循关系完整性约束。

•分类：按存储数据的性质可分为基础表（存储原始数据，独立存在）和派生表（由查询结果生成，临时存在）；按存储引擎可分为 InnoDB 表（支持事务、外键）、MyISAM 表（不支持事务、外键，查询效率高）等。

•与其他对象的关联：表是索引、视图、触发器的基础，索引建立在表的字段上，视图基于表的查询结果生成，触发器绑定在表上并响应表的 DML 操作。

3.1.2 索引（Index）

索引是为提升数据查询效率而创建的数据库对象，本质是基于表中一个或多个字段构建的有序数据结构（如 B+树、哈希表），通过快速定位数据地址，减少表扫描的次数，避免全表查询的低效性。

3.1.2.1 索引的核心作用

•提升查询效率：针对查询频繁的字段建立索引，可快速匹配查询条件，大幅缩短查询时间（尤其数据量大时）。

P24

•维护数据唯一性：唯一索引、主键索引可强制字段值的唯一性，避免重复数据录入，辅助保证实体完整性。

3.1.2.2 常见索引类型

•按功能分类：

•主键索引（Primary Key Index）：自动为表的主键字段创建，唯一且非空，一个表仅能有一个主键索引，用于唯一标识每条记录。

•唯一索引（Unique Index）：强制字段值唯一，允许字段值为空，一个表可创建多个唯一索引（如邮箱、手机号字段）。

•普通索引（Normal Index）：无唯一性约束，仅用于提升查询效率，可创建在任意字段上，一个表可创建多个普通索引。

•全文索引（Full-Text Index）：用于文本类型字段（如 varchar、text）的模糊查询，支持关键词匹配，适用于大量文本数据的检索（MySQL 仅 InnoDB、MyISAM 支持）。

按结构分类：

•B+树索引：主流索引结构，适用于范围查询、排序查询，所有数据都存储在叶子节点，非叶子节点仅存储索引值，查询效率稳定。

•哈希索引：基于哈希表实现，适用于等值查询（如=、IN），查询速度极快，但不支持范围查询、排序，MySQL 中 Memory 存储引擎默认使用哈希索引。

•聚簇索引与非聚簇索引：聚簇索引将索引结构与数据存储在一起（主键索引默认是聚簇索引），查询时无需回表；非聚簇索引仅存储索引值和数据地址，查询时需通过地址回表取数据。

按字段数量分类：

•单列索引：基于单个字段创建的索引，适用于单个字段的查询条件。

•联合索引（复合索引）：基于多个字段组合创建的索引，遵循“最左前缀匹配原则”，查询时需匹配索引的最左字段才能触发索引生效，适用于多字段组合查询。

3.1.2.3 索引的设计原则与注意事项

•设计原则：优先为查询频繁、过滤性强的字段建立索引；避免为频繁更新、插入的字段建立索引（维护索引会降低写入效率）；联合索引需合理安排字段顺序（过滤性强的字段放左侧）；避免过度建索引（索引会占用额外存储空间）。

•注意事项：索引仅能提升查询效率，会降低插入、更新、删除的效率（需同步维护索引结构）；空值较多的字段不适合建索引（索引无法有效匹配空值）；小表无需建索引（全表查询效率高于索引查询）。

3.1.3 视图（View）

视图是基于一个或多个表（或其他视图）的查询结果构建的虚拟表，不存储实际数据，仅存储查询语句（视图定义），数据来源于底层的基表，当基表数据发生变化时，视图数据会同步更新。

3.1.3.1 视图的核心作用

•简化查询：将复杂的多表连接、聚合查询封装视图，用户无需编写复杂 SQL，直接查询视图即可获取所需数据。

P25

•隐藏数据细节：仅向用户展示所需字段，隐藏敏感数据或无关字段，提升数据安全性。

•控制数据访问权限：可针对视图分配查询权限，无需给用户分配基表的访问权限，实现精细化权限控制。

•统一数据展示：多个应用程序可通过同一视图获取数据，保证数据展示的一致性，减少数据冗余。

3.1.3.2 视图的分类

•按是否可更新分类：

•可更新视图：视图定义中不包含聚合函数、DISTINCT、GROUP BY、UNION、子查询等，可通过视图执行 INSERT、UPDATE、DELETE 操作，修改会同步到基表。

•不可更新视图：包含聚合函数、DISTINCT 等限制条件，无法执行 DML 操作，仅用于查询。

按创建方式分类：

•简单视图：基于单个表创建，无复杂查询逻辑，仅包含字段筛选、条件筛选等简单操作。

•复杂视图：基于多个表连接、包含聚合函数、子查询等复杂逻辑创建，适用于复杂业务场景的查询。

3.1.3.3 视图的注意事项

•视图不存储数据，查询视图本质是执行底层的 SELECT 语句，查询效率依赖于基表的索引设计。

•删除视图不会影响基表数据，仅删除视图定义；修改基表结构（如删除字段）可能导致视图失效，需同步修改视图定义。

•WITH CHECK OPTION 约束：创建视图时添加该约束，可确保通过视图插入、修改的数据符合视图的查询条件，避免插入/修改后的数据无法通过视图查询到。

3.1.4 存储过程（Stored Procedure）

存储过程是一组预先编译好的、可重复执行的 SQL 语句集合，封装了复杂的业务逻辑，存储在数据库中，用户可通过调用存储过程的名称执行对应的 SQL 逻辑，无需重复编写 SQL 语句。

3.1.4.1 存储过程的核心特性

•预编译：存储过程创建时会被 DBMS 编译，后续调用时无需重新编译，提升执行效率。

•可复用：封装的业务逻辑可被多个应用程序、多个用户重复调用，减少代码冗余，保证业务逻辑的一致性。

•支持参数：可接收输入参数（IN）、输出参数（OUT）、输入输出参数（INOUT），适配不同的业务场景。

•安全性高：可针对存储过程分配执行权限，用户无需直接操作基表，避免误操作；同时隐藏 SQL 逻辑，防止敏感 SQL 泄露。

•支持流程控制：可包含 IF-ELSE、循环（WHILE、FOR）、分支等流程控制语句，实现复杂的业务逻辑（如数据校验、批量处理）。

3.1.4.2 存储过程的基本语法

SQL

3.1.4.3 存储过程的优缺点

•优点：提升执行效率、减少网络传输（仅传递调用指令，无需传递大量 SQL 语句）、封装业务逻辑、提升安全性、可复用。

•缺点：调试困难（多数 DBMS 不支持存储过程的分步调试）、可移植性差（不同 DBMS 的存储过程语法差异较大）、维护成本高（修改存储过程需重新编译，影响依赖它的应用）、占用数据库资源。

3.1.5 触发器（Trigger）

触发器是一种特殊的存储程序，无需手动调用，当表发生指定的 DML 操作（INSERT、UPDATE、DELETE）时，会自动触发执行，常用于实现数据完整性校验、数据同步、日志记录等场景。

P27

3.1.5.1 触发器的核心特性

•自动触发：无需用户手动调用，触发条件满足时（执行指定 DML 操作）自动执行。

•绑定表：触发器必须绑定在某个具体的表上，仅能响应该表的 DML 操作，无法独立存在。

•无法直接调用：仅能通过触发条件触发，不能通过 CALL 语句调用。

•支持新旧数据访问：触发时可访问操作前的旧数据（OLD）和操作后的新数据（NEW），用于数据校验或同步。

3.1.5.2 触发器的分类

•按触发时机分类：

•BEFORE 触发器：在 DML 操作执行前触发，常用于数据校验（如校验字段值合法性），若校验失败，可阻止 DML 操作执行。

•AFTER 触发器：在 DML 操作执行后触发，常用于日志记录、数据同步（如操作后记录日志、同步数据到其他表）。

按触发事件分类：

•INSERT 触发器：执行 INSERT 操作时触发。

•UPDATE 触发器：执行 UPDATE 操作时触发。

•DELETE 触发器：执行 DELETE 操作时触发。

3.1.5.3 触发器的基本语法

CREATE TRIGGER 触发器名 触发时机 触发事件 ON 表名
FOR EACH ROW -- 行级触发器，每操作一行触发一次（MySQL 仅支持行级触发器）

-- 触发器逻辑（SQL 语句）

-- 查看触发器

3.1.5.4 触发器的注意事项

•触发器中不能包含 START TRANSACTION、COMMIT、ROLLBACK 语句（会干扰触发操作的事务）。

•避免在触发器中执行复杂操作（如大量数据插入、多表连接），否则会降低 DML 操作的执行效率。

•触发器的逻辑需简洁，若业务逻辑复杂，建议使用存储过程替代，便于调试和维护。

3.1.6 其他数据库对象

•序列（Sequence）：用于生成唯一的递增或递减数值，常用于主键字段的自动赋值（Oracle、PostgreSQL 支持，MySQL 通过自增字段 AUTO_INCREMENT 替代），可避免主键值重复。

•同义词（Synonym）：给数据库对象（表、视图、存储过程等）起别名，简化对象名称的使用，同时隐藏对象的真实名称和存储位置，提升可移植性。

•存储函数（Stored Function）：与存储过程类似，是预先编译的 SQL 语句集合，但必须返回一个值，可用于复杂的计算逻辑（如数据格式化、数值计算），可在 SELECT 语句中直接调用。

3.2 数据库完整性

数据库完整性是指数据库中的数据始终保持合法、有效、一致的特性，是数据库系统的核心要求之一，通过各类约束条件、数据库对象（触发器、主键等）实现，避免无效数据、错误数据的录入，防止数据不一致。

数据库完整性分为实体完整性、参照完整性、用户定义完整性三类，同时还包括域完整性、数据一致性等延伸要求。

3.2.1 实体完整性

实体完整性是指保证数据库中每个实体（表中的每条记录）都能被唯一标识，无重复记录、无主键为空的记录，是最基础的完整性约束，核心通过主键约束、唯一约束实现。

3.2.1.1 实现方式

•主键约束（Primary Key）：

•每个表有且仅有一个主键，主键可以是单个字段，也可以是多个字段组成的复合主键。

•主键字段的值必须唯一、非空，一旦设置主键约束，DBMS 会自动阻止主键为空、主键重复的记录插入或更新。

•示例：学生表中，学号（sid）作为主键，设置主键约束后，无法插入学号为空或学号重复的学生记录。

唯一约束（Unique）：

•用于保证字段值的唯一性，可作为实体完整性的补充，一个表可创建多个唯一约束。

•与主键约束的区别：唯一约束允许字段值为空（但仅允许一个空值），而主键约束不允许为空；主键约束会自动创建主键索引，唯一约束会自动创建唯一索引。

•示例：学生表中，邮箱（email）设置唯一约束，避免多个学生使用同一个邮箱。

3.2.1.2 违反实体完整性的后果

若插入或更新记录时违反实体完整性（如主键为空、主键重复、唯一约束字段值重复），DBMS 会直接拒绝操作，并返回错误提示，确保数据无法录入数据库。

3.2.2 参照完整性

参照完整性又称引用完整性，用于维护两个表之间的关联关系（通过外键与主键的关联），确保外键的值要么为空，要么等于被引用表（主表）中对应的主键值，避免引用无效数据，是多表关联的核心完整性约束。

3.2.2.1 核心概念

•主表：被引用的表，包含主键字段，是关联关系的核心表（如班级表 class，主键为班级号 cid）。

•子表：引用主表的表，包含外键字段，外键字段的值引用主表的主键值（如学生表 student，外键为班级号 cid，引用班级表的 cid）。

•外键约束（Foreign Key）：绑定在子表的外键字段上，用于定义子表与主表的关联关系，是实现参照完整性的核心。

3.2.2.2 参照完整性的规则

•子表插入记录时，外键字段的值必须要么为空，要么在主表的主键字段中存在，否则无法插入。

•子表更新记录时，修改后的外键值必须要么为空，要么在主表的主键字段中存在，否则无法更新。

•主表删除或更新主键记录时，需处理子表的关联记录，避免子表出现无效的外键值，常用处理方式有三种：

•RESTRICT（默认）：拒绝删除或更新主表记录，若子表存在关联记录，DBMS 直接返回错误。

P30

•CASCADE（级联操作）：删除主表记录时，自动删除子表的关联记录；更新主表主键时，自动更新子表的外键值，适用于主表与子表为“从属关系”的场景（如班级删除，对应学生也删除）。

•SET NULL：删除主表记录时，将子表的外键值设为 null（需保证子表外键字段允许为空），适用于子表记录可独立存在的场景。

3.2.3 用户定义完整性

用户定义完整性是根据具体的业务需求，自定义的约束条件，用于限制字段的取值范围、格式、长度等，弥补实体完整性和参照完整性的不足，适用于各类个性化的业务场景。

3.2.3.1 常见实现方式

•非空约束（NOT NULL）：

•强制字段值不能为空，用于保证必填字段的数据完整性（如学生姓名、学号）。

•示例：学生表中，姓名（sname）设置非空约束，无法插入姓名为空的学生记录。

P31

检查约束（CHECK）：

•自定义字段的取值条件，仅允许满足条件的值录入，适用于限制字段的取值范围、格式等。

•示例：学生表中，年龄（age）设置检查约束，限制年龄在 0-150 之间；性别（gender）设置检查约束，仅允许录入“男”或“女”。

•注意：MySQL 5.7 及以下版本不支持 CHECK 约束（语法兼容但不生效），需通过触发器实现：MySQL 8.0 及以上版本支持 CHECK 约束。

默认值约束（DEFAULT）：

•为字段设置默认值，当插入记录时未给该字段赋值，DBMS 会自动填入默认值，避免字段值为空（非必填字段）。

•示例：学生表中，性别（gender）设置默认值为“男”，插入学生时未指定性别，自动赋值为“男”。

触发器实现自定义完整性：

•对于复杂的业务完整性需求（如多字段联动校验、数据格式校验），可通过触发器实现，比 CHECK 约束更灵活。

•示例：创建触发器，校验学生的入学日期不能晚于当前日期，若违反则拒绝插入。

3.2.4 完整性约束的总结

完整性类型核心目的实现方式
实体完整性唯一标识实体，无重复、无主键为空主键约束、唯一约束
参照完整性维护多表关联关系，避免无效引用外键约束（级联操作、SET NULL 等）
用户定义完整性满足个性化业务需求，限制数据取值非空约束、检查约束、默认值约束、触发器

完整性约束的优先级：实体完整性 > 参照完整性 > 用户定义完整性，DBMS 会优先校验基础完整性，再校验关联和自定义完整性。

4.1 数据库并发访问概述

4.1.1 并发访问的定义与场景

数据库并发访问是指多个用户或应用程序同时对数据库中的数据执行操作（查询、插入、更新、删除），是数据库系统的常见场景，如电商平台多个用户同时下单、企业系统多个员工同时操作客户数据、教务系统批量处理选课信息等。

P32

并发访问的核心需求：在保证多个操作正常执行的同时，维护数据的完整性和一致性，避免并发带来的各类问题，兼顾系统吞吐量与数据可靠性。

4.1.2 并发访问的优势与问题

•优势：提升数据库服务器资源利用率和系统吞吐量，减少用户等待时间；支持多用户同时操作，适配大规模应用场景：提高数据的实时性和可用性，满足业务连续运行需求。

•问题（并发异常）：多个操作同时执行时，若缺乏有效的控制，会导致数据不一致，出现各类并发异常，本质是事务隔离性被破坏，常见的有脏读、不可重复读、幻读、丢失修改。

4.1.3 常见并发异常

•脏读（Dirty Read）：

○定义：一个事务读取了另一个事务未提交的修改数据，若后续该事务回滚，读取到的数据就是“脏数据”（无效数据），导致读取结果不可靠。

○示例：事务 A 修改了学生的年龄为 25，但未提交；事务 B 读取到该学生的年龄为 25；随后事务 A 因错误回滚，学生年龄恢复为 20，事务 B 读取到的 25 就是脏数据，基于该数据的后续操作会出现偏差。

•不可重复读（Non-Repeatable Read）：

○定义：同一事务内，多次读取同一数据，结果不一致（因其他事务修改并提交了该数据），违反了事务的隔离性和一致性要求。

○示例：事务 A 第一次读取学生年龄为 20；事务 B 修改该学生年龄为 22 并提交；事务 A 再次读取该学生年龄，结果为 22，两次读取结果不一致，影响事务内逻辑判断。

•幻读（Phantom Read）：

○定义：同一事务内，多次执行相同的查询语句，查询结果的记录条数不一致（因其他事务插入或删除了符合查询条件的记录），与不可重复读的区别是：不可重复读是单条数据修改，幻读是记录增减。

○示例：事务 A 查询班级号为 101 的学生，得到 3 条记录；事务 B 插入一条班级号为 101 的学生记录并提交；事务 A 再次执行相同查询，得到 4 条记录，出现“幻影”记录，导致事务内统计结果不准确。

•丢失修改（Lost Update）：

○定义：两个事务同时修改同一条记录，后提交的事务覆盖了先提交事务的修改，导致先提交的修改丢失，破坏数据一致性。

○示例：事务 A 读取学生年龄为 20，准备修改为 21；事务 B 同时读取该学生年龄为 20，准备修改为 22；事务 A 先提交，学生年龄变为 21；事务 B 再提交，将年龄改为 22，覆盖了事务 A 的修改，事务 A 的修改丢失。

4.2 并发控制技术

并发控制技术是用于解决并发异常、维护数据一致性的核心技术，DBMS 通过各类机制控制多个事务的执行顺序和访问权限，平衡并发性能与数据可靠性，常用的并发控制技术包括锁机制、事务隔离级别、乐观并发控制、悲观并发控制、MVCC 机制等。

4.2.1 锁机制

锁是并发控制的最基础机制，本质是一种访问权限控制，DBMS 通过给数据库对象（表、行、字段、数据页）加锁，限制其他事务对该对象的操作，避免并发修改冲突，实现事务的隔离性。锁的核心是“控制访问权限”，通过合理的锁定策略，减少冲突、提升并发效率。

4.2.1.1 锁的分类

•按锁定对象分类：

○表锁（Table Lock）：锁定整个表，对表中的所有记录生效，锁定粒度大，并发性能差，适用于大量数据批量操作（如 TRUNCATE、批量更新、全表查询）。

•优点：锁定速度快，开销小，无需逐行判断锁定对象，适合大批量操作。

•缺点：并发性能差，一个事务锁定表后，其他事务无法对该表执行 DML 操作（读锁除外），容易造成阻塞。

•类型：读锁（共享锁，S 锁）、写锁（排他锁，X 锁）。

○行锁（Row Lock）：锁定表中的单条或多条记录，锁定粒度小，并发性能好，适用于单条记录修改、查询场景（如 MySQL InnoDB 存储引擎支持行锁）。

•优点：并发性能好，多个事务可同时锁定表中的不同行，互不干扰，减少阻塞。

•缺点：锁定速度慢，开销大，需逐行锁定，可能出现死锁，锁定范围易受索引影响（无索引时会升级为表锁）。

•类型：读锁（共享锁，S 锁）、写锁（排他锁，X 锁）、意向锁（用于表锁与行锁的协调）。

○页锁（Page Lock）：锁定数据页（数据库存储的基本单位，一个页包含多条记录，如 MySQL 中默认页大小为 16KB），锁定粒度介于表锁和行锁之间，适用于中等粒度的并发场景（如 SQL Server、DB2 支持页锁）。

•优点：兼顾锁定速度与并发性能，避免表锁的高阻塞和行锁的高开销。

•缺点：可能出现不必要的锁定（锁定页内无关记录），仍存在一定的阻塞问题。

•按锁的兼容性分类：

○共享锁（S 锁，读锁）：多个事务可同时对同一对象加共享锁，仅允许读取数据，不允许修改数据。共享锁之间兼容，共享锁与排他锁不兼容（一个对象加了 S 锁，无法加 X 锁，反之亦然）。

P34

○排他锁（X 锁，写锁）：一个事务对对象加排他锁后，仅该事务可对对象执行修改、读取操作，其他事务无法对该对象加任何锁（共享锁、排他锁均不允许）。排他锁之间不兼容，避免并发修改冲突。

○意向锁：用于告知 DBMS“某个事务即将对表中的行加锁”，分为意向共享锁（IS 锁）和意向排他锁（IX 锁），避免表锁与行锁的冲突，提升锁定效率。意向锁仅作用于表级，不影响行级操作。

•按锁定方式分类：

○自动锁：由 DBMS 自动添加和释放，无需用户手动操作（如 InnoDB 执行 UPDATE、DELETE 时自动给行加排他锁，查询时默认不加锁，通过 MVCC 实现读不加锁）。

○手动锁：由用户通过 SQL 语句手动添加和释放，适用于复杂的并发场景（如 MySQL 中通过 LOCK TABLES 手动加表锁，UNLOCK TABLES 释放锁；通过 SELECT … FOR UPDATE 手动加行级排他锁）。

4.2.1.3 死锁

死锁是锁机制的常见问题，指两个或多个事务相互持有对方需要的锁，且都无法释放自己的锁，导致所有事务陷入无限等待的状态，无法继续执行，最终需外力干预才能解除。

•死锁产生的条件（四大必要条件，缺一不可）：

○互斥条件：锁的资源只能被一个事务持有，无法被多个事务同时持有（锁的核心特性）。

○请求与保持条件：事务持有一个锁后，又请求另一个被其他事务持有的锁，且不释放自己已持有的锁。

○不可剥夺条件：事务持有的锁无法被其他事务强制剥夺，只能由持有事务主动释放。

○循环等待条件：多个事务形成循环等待链，每个事务都等待下一个事务持有的锁。

•死锁的解决方法：

○预防死锁：破坏死锁的四大必要条件，从根源上避免死锁。如按固定顺序访问数据库对象（如所有事务均先访问学生表再访问班级表），避免循环等待；采用超时机制，超过指定时间自动释放锁，破坏请求与保持条件。

P35

○检测与解除死锁：DBMS 定期检测死锁（如通过锁等待图检测，若图中存在循环，则判定为死锁），一旦发现死锁，选择一个代价最小的事务（如执行时间最短、修改数据最少的事务）强制回滚，释放锁，解除死锁（MySQL、Oracle 均支持自动检测和解除死锁）。

○避免死锁：优化事务逻辑，缩短事务执行时间，减少锁的持有时间：避免同时持有多个锁，尽量一次性获取所需的所有锁；减少长事务，避免事务长时间占用锁资源。

4.2.2 事务隔离级别

事务隔离级别是用于控制事务隔离程度的机制，通过设置不同的隔离级别，可解决不同的并发异常，平衡并发性能和数据一致性。事务的四大特性（ACID）中，隔离性就是通过隔离级别实现的，SQL 标准定义了四个隔离级别，不同 DBMS 的支持程度不同，且默认隔离级别存在差异。

隔离级别核心逻辑：隔离级别越高，数据一致性越强，但并发性能越差；隔离级别越低，并发性能越好，但数据一致性越弱。

4.2.2.1 四大隔离级别（从低到高）

•读未提交（READ UNCOMMITTED）：

○核心规则：允许一个事务读取另一个事务未提交的修改数据，是最低的隔离级别。

○并发异常：允许脏读、不可重复读、幻读、丢失修改，无任何隔离效果。

○适用场景：对数据一致性要求极低，追求极致并发性能的场景（极少使用），如实时监控数据（允许临时数据偏差）。

○DBMS 支持：大多数 DBMS 均支持，但无默认使用该级别的场景。

•读已提交（READ COMMITTED）：

○核心规则：允许一个事务读取另一个事务已提交的修改数据，禁止脏读（仅读取已提交数据）。

○并发异常：允许不可重复读、幻读，避免脏读、丢失修改。

○适用场景：对数据一致性有基本要求，追求较高并发性能的场景（Oracle、SQL Server、PostgreSQL 默认隔离级别），如电商订单查询、用户信息查询。

○实现逻辑：通过“瞬间读”机制，每次查询均读取当前已提交的数据，避免读取未提交的脏数据。

•可重复读（REPEATABLE READ）：

○核心规则：保证同一事务内，多次读取同一数据的结果一致，禁止脏读、不可重复读。

P36

○并发异常：理论上允许幻读，但 MySQL 通过 MVCC（多版本并发控制）机制避免了幻读，实际可杜绝四种异常中的三种。

○适用场景：对数据一致性要求较高，兼顾并发性能的场景（MySQL 默认隔离级别），如财务数据录入、学生成绩管理。

○实现逻辑：事务启动后，读取的数据均为事务启动时的快照版本，后续其他事务的修改的提交数据，不会影响当前事务的读取结果。

•串行化（SERIALIZABLE）：

○核心规则：强制事务串行执行（一个事务执行完成后，另一个事务再执行），相当于禁止并发，是最高的隔离级别。

○并发异常：无任何并发异常，完全保证数据一致性，严格遵循 ACID 的隔离性要求。

○适用场景：对数据一致性要求极高，不追求并发性能的场景（如金融交易、财务结算、审计数据处理）。

○缺点：并发性能极差，容易造成大量事务阻塞，适合数据操作频率低、一致性要求极高的场景。

4.2.3 其他并发控制技术

•MVCC（多版本并发控制）：

○定义：一种无锁并发控制技术，通过为数据维护多个版本（快照），让不同事务访问不同版本的数据，实现“读不加锁、写不阻塞读”，提升并发性能。

○核心原理：事务启动时，会获取一个当前的版本号，读取数据时仅读取版本号小于等于当前事务版本号的数据，写入数据时会生成一个新的版本号，不影响旧版本数据的读取。

○适用场景：MySQL InnoDB、PostgreSQL 等主流数据库，是实现可重复读隔离级别的核心机制。

•乐观并发控制（OCC）：

○定义：基于“乐观”假设，认为并发冲突概率极低，不主动加锁，仅在事务提交时检测是否存在冲突，若存在冲突则回滚事务，重新执行。

○核心流程：读取数据时记录数据版本号 → 事务内修改数据 → 提交时对比版本号，若一致则提交（更新版本号），若不一致则回滚。

○适用场景：并发冲突少、读多写少的场景（如博客系统、新闻网站），避免锁机制的开销。

•悲观并发控制（PCC）：

○定义：基于“悲观”假设，认为并发冲突概率极高，每次操作数据时都主动加锁，阻止其他事务修改，避免冲突。

○核心原理：与锁机制完全结合，读取时加共享锁，修改时加排他锁，确保操作期间数据不被其他事务修改。

○适用场景：并发冲突多、写多读少的场景（如电商下单、库存扣减），保证数据一致性。

4.3 数据库备份与恢复

数据库备份与恢复是保障数据库数据安全的核心手段，用于应对数据丢失、数据损坏、系统故障等场景（如硬件故障、软件崩溃、误操作、病毒攻击）。备份是将数据库数据或日志复制到其他存储介质的过程，恢复是将备份数据还原到数据库，恢复数据一致性和可用性的过程。

4.3.1 备份与恢复的核心目标

•数据可恢复：确保备份数据完整、有效，出现故障时能快速还原数据，减少数据丢失。

•最小化停机时间：优化恢复流程，缩短数据库不可用的时间，降低业务损失。

•保证数据一致性：恢复后的数据需符合业务逻辑，不出现数据错乱、丢失等问题，遵循 ACID 特性。

4.3.2 备份的分类

数据库备份可按不同维度分类，核心分类包括按备份范围、按备份状态、按备份方式、按备份内容四类，不同分类的备份适用于不同场景，可组合使用以提升备份可靠性。

4.3.2.1 按备份范围分类

•全量备份（Full Backup）：

○定义：对整个数据库的所有数据（表、索引、视图、存储过程等所有数据库对象）进行完整备份，是最基础、最全面的备份方式。

○优点：备份数据完整，恢复时仅需使用全量备份文件，流程简单，无需依赖其他备份。

○缺点：备份时间长、占用存储空间大，适合数据量不大或备份频率低的场景（如每天凌晨全量备份）。

○适用场景：首次备份、每周/每月全量备份，作为增量备份、差异备份的基础。

•增量备份（Incremental Backup）：

○定义：仅备份上一次备份（全量或增量）后发生变化的数据，不备份未修改的数据，依赖上一次备份的基础数据。

○优点：备份时间短、占用存储空间小，备份效率高，适合数据量较大、修改频繁的场景。

○缺点：恢复流程复杂，需先恢复全量备份，再依次恢复所有增量备份，若中间某一个增量备份文件损坏，后续增量备份无法使用。

○适用场景：每天多次增量备份（如每 6 小时一次），减少全量备份的频率和开销。

•差异备份（Differential Backup）：

○定义：仅备份上一次全量备份后发生变化的数据，不依赖增量备份，仅依赖上一次全量备份。

○优点：备份效率高于全量备份，恢复流程比增量备份简单（仅需恢复全量备份+最新差异备份），数据可靠性高于增量备份。

○缺点：占用存储空间比增量备份大（每次备份均包含上一次全量备份后的所有修改数据），备份时间随修改数据量增加而变长。

○适用场景：每天一次差异备份，搭配每周一次全量备份，兼顾效率与可靠性。

4.3.2.2 按备份状态分类

•热备份（Online Backup）：

○定义：备份过程中，数据库正常运行，用户可正常执行查询、插入、更新、删除等操作，不影响业务正常运行，又称在线备份。

○优点：不中断业务，适合 7×24 小时运行的核心业务系统（如电商、金融系统）。

○缺点：备份过程中可能产生数据不一致，需配合日志备份解决；备份开销较大，可能影响数据库并发性能。

○适用场景：核心业务数据库，需持续提供服务，无法停机的场景。

○支持 DBMS：MySQL InnoDB、Oracle、SQL Server 等主流数据库均支持。

•冷备份（Offline Backup）：

○定义：备份过程中，需停止数据库服务，禁止用户操作，确保数据不被修改，又称离线备份。

○优点：备份数据一致性高，无数据冲突，备份流程简单，开销小。

○缺点：中断业务，影响用户使用，适合非核心业务或可停机维护的场景（如夜间维护）。

○适用场景：非核心业务数据库、测试环境数据库，或可安排停机维护的场景。

○操作方式：停止 DBMS 服务 → 复制数据库数据文件 → 启动 DBMS 服务。

•温备份（Warm Backup）：

○定义：介于热备份与冷备份之间，备份过程中数据库正常运行，但仅允许读取操作，禁止写入操作（插入、更新、删除）。

○优点：数据一致性较高，无需完全停止数据库服务，仅限制写入操作。

○缺点：影响写入业务，适合读取频率高、写入频率低的场景（如报表数据库）。

4.3.2.3 按备份方式分类

•物理备份（Physical Backup）：

○定义：直接复制数据库的物理文件（如数据文件、日志文件、配置文件），不关心数据的逻辑结构，备份的是文件本身。

○优点：备份速度快、恢复速度快，适合大数据量数据库；与数据库类型无关，通用性强。

○缺点：备份文件与操作系统、DBMS 版本相关，可移植性差；无法精准备份单个表或部分数据，只能备份整个数据库或数据文件。

○操作方式：复制数据目录（如 MySQL 的 data 目录）、使用 DBMS 自带工具（如 MySQL 的 mysqlbackup）。

•逻辑备份（Logical Backup）：

○定义：备份数据库的逻辑结构和数据，生成 SQL 语句文件或文本文件（如 CREATE TABLE、INSERT 语句），备份的是数据的逻辑内容，而非物理文件。

○优点：可移植性强，不受操作系统、DBMS 版本限制；可精准备份单个表、单个数据库或部分数据，灵活度高；备份文件体积小（可压缩）。

○缺点：备份速度慢、恢复速度慢（需执行大量 SQL 语句），适合小数据量数据库；备份过程中可能出现数据不一致。

○操作方式：使用 DBMS 自带工具（如 MySQL 的 mysqldump、Oracle 的 expdp/impdp）。

4.3.2.4 按备份内容分类

•数据备份：备份数据库中的核心数据（表数据、索引、视图、存储过程等数据库对象），是备份的核心内容，用于恢复数据本身。

•日志备份：备份数据库的事务日志（如 MySQL 的 binlog、Oracle 的 redo log），用于恢复全量备份后的数据修改，实现“点时间恢复”（恢复到某一具体时间点的数据）。

•配置备份：备份数据库的配置文件（如 MySQL 的 my.cnf、Oracle 的 listener.ora），用于恢复数据库服务的配置，避免重新配置的麻烦。

4.3.4 数据库恢复

数据库恢复是将备份数据还原到数据库的过程，核心是根据备份类型和故障场景，选择合适的恢复策略，确保恢复后的数据完整、一致。恢复的核心原则：“备份决定恢复”，恢复流程依赖于备份方式，不同备份类型的恢复流程不同。

4.3.4.1 恢复的核心流程

1. 故障诊断：确定故障类型（如硬件故障、软件故障、误操作、数据损坏），判断数据丢失范围，选择对应的备份文件。

2. 准备工作：停止数据库服务（冷恢复）或限制写入操作（热恢复），备份当前剩余的数据和日志（避免二次损坏），确认备份文件完整有效。

3. 执行恢复：根据备份类型，依次还原备份数据（全量备份→差异备份/增量备份→日志备份），确保数据逐层还原，不遗漏修改。

4. 一致性校验：恢复完成后，启动数据库服务，校验数据完整性（如查询关键数据、对比数据量、执行业务逻辑测试），确保数据无错乱、无丢失。

5. 业务恢复：确认数据无误后，开放数据库服务，恢复正常业务操作。

4.3.4.2 不同备份类型的恢复策略

•全量备份恢复：

○核心流程：仅需还原全量备份文件，无需依赖其他备份，流程最简单。

○适用场景：仅丢失全量备份后的数据，或无增量、差异备份的场景。

○缺点：恢复后的数据是全量备份时的状态，全量备份后的修改数据会丢失。

•增量备份恢复：

○核心流程：先还原上一次全量备份 → 依次还原所有增量备份（按备份时间顺序） → 还原日志备份（可选，实现点时间恢复）。

P45

○注意事项：必须按顺序还原增量备份，不能遗漏或颠倒顺序；若某一个增量备份文件损坏，后续增量备份无法使用，只能恢复到上一个增量备份的状态。

○适用场景：数据修改频繁，已做全量+多次增量备份的场景。

•差异备份恢复：

○核心流程：先还原上一次全量备份 → 还原最新的差异备份 → 还原日志备份（可选）。

○优点：恢复流程比增量备份简单，无需依次还原所有差异备份，仅需最新的差异备份。

○适用场景：已做全量+每日差异备份的场景，兼顾效率与可靠性。

•点时间恢复：

○定义：恢复到某一具体时间点的数据，用于解决误操作（如误删除表、误修改数据），需结合全量备份+日志备份实现。

○核心流程：还原全量备份 → 还原差异/增量备份 → 还原日志备份，执行日志回放，停止到目标时间点。

○示例（MySQL）：

# 1. 还原全量备份
mysql -u 用户名 -p 密码 < 全量备份文件.sql

# 2. 回放 binlog 日志，恢复到指定时间点（如 2024-05-01 10:00:00）
mysqlbinlog --start-datetime="2024-05-01 00:00:00" --stop-datetime="2024-05-01 10:00:00" 二进制日志文件 |
mysql -u 用户名 -p 密码

4.3.4.3 常见故障及恢复方案

•硬件故障（如硬盘损坏）：

○恢复方案：更换故障硬件 → 重新安装操作系统和 DBMS → 按流程还原全量备份+差异/增量备份+日志备份 → 校验数据一致性。

•软件故障（如 DBMS 崩溃）：

•恢复方案：重启 DBMS 服务（简单故障可解决） → 若无法启动，重新安装 DBMS → 还原备份数据 → 校验数据。

•误操作（如误删除表、误修改数据）：

○恢复方案：若有最近的全量+差异/增量备份，执行点时间恢复（恢复到误操作前的时间点）；若无备份，可尝试使用 DBMS 自带的恢复工具（如 MySQL 的 binlog 日志回放、Oracle 的闪回技术），若工具无法恢复，则需依赖专业数据恢复软件，尽可能减少数据丢失。

○数据损坏（如表损坏、数据文件损坏）：

○恢复方案：先通过 DBMS 自带的检测工具（如 MySQL 的 mysqlcheck、Oracle 的 DBVERIFY）检测损坏范围：若损坏范围较小，可使用修复工具（如 MySQL 的 myisamchk）修复；若修复失败，需还原备份数据（全量+差异/增量+日志），覆盖损坏数据，确保数据一致性。

○病毒/恶意攻击：

○恢复方案：先隔离受攻击的数据库服务器，清除病毒或恶意程序，修补系统和 DBMS 漏洞；再还原最近的、未受污染的备份数据（优先使用离线备份），避免使用受攻击后的备份；恢复后启用安全防护措施（如权限管控、数据加密、日志审计），防止再次攻击。

4.4 备份与恢复的最佳实践

结合业务场景和数据安全需求，制定合理的备份与恢复策略，兼顾可靠性、效率和成本，以下是行业通用的最佳实践：

○备份策略组合：采用“全量备份+差异/增量备份+日志备份”的组合方式，平衡备份效率和恢复完整性。例如：每周日凌晨执行全量备份，周一至周六凌晨执行差异备份，每 6 小时执行一次日志备份，确保数据丢失量控制在可接受范围。

○备份存储管理：备份文件需异地存储（避免与数据库服务器在同一硬件设备上），防止本地硬件故障导致备份文件丢失；定期清理过期备份文件，采用压缩存储减少空间占用；对备份文件进行校验（如 MD5 校验），确保备份文件完整有效。

○定期测试恢复流程：每月至少执行一次恢复测试，模拟不同故障场景（如误操作、硬件故障），验证备份文件的可用性和恢复流程的可行性，优化恢复步骤，缩短恢复时间；记录恢复测试结果，形成恢复手册，便于运维人员快速参考。

○事务与备份协同：热备份时，确保事务日志正常记录，避免备份过程中事务中断导致数据不一致；备份完成后，及时备份事务日志，确保可实现点时间恢复：长事务需避开备份高峰，减少备份与业务的冲突。

○权限管控：严格控制备份与恢复操作的权限，仅授权给核心运维人员；记录备份与恢复操作日志（如操作人、操作时间、操作内容），便于审计和问题追溯；禁止非授权人员访问备份文件，防止数据泄露。

5.1 数据库系统设计概述

5.1.1 数据库设计的定义与目标

数据库系统设计是指根据业务需求，构建符合数据一致性、完整性、安全性和性能要求的数据库结构（包括表结构、索引、视图、约束等），并设计对应的应用程序接口，实现数据的有效存储、管理和访问的过程。

数据库设计的核心目标：

○满足业务需求：准确映射业务逻辑，支持所有业务操作（查询、插入、更新、删除），确保数据存储与业务流程匹配。

○保证数据质量：通过约束、规范设计，确保数据的完整性、一致性和准确性，避免数据冗余、数据错乱。

○优化性能：合理设计表结构、索引和存储方式，提升数据访问速度，降低数据库负载，适配业务并发需求。

○具备可扩展性：设计灵活的数据库结构，支持业务后续迭代升级（如新增字段、新增表），减少重构成本。

○保障安全性：设计合理的权限体系和数据加密方案，防止数据泄露、篡改和非法访问。

5.1.2 数据库设计的流程

数据库设计是一个循序渐进、迭代优化的过程，遵循“需求分析→概念结构设计→逻辑结构设计→物理结构设计→数据库实施→数据库运行与维护”的六阶段流程，各阶段紧密衔接，确保设计成果符合预期。

核心原则：自上而下、逐步细化，先明确业务需求，再转化为数据模型，最后落地物理数据库，每个阶段完成后需进行评审，合格后进入下一阶段，避免后期返工。

5.1.3 数据库设计的核心原则

○原子性原则：表中的字段需满足原子性，即字段值不可再拆分，避免存储复合数据（如将“姓名+电话”存储在一个字段中），便于数据查询和修改。

○减少冗余原则：合理设计表结构，通过关联关系减少数据冗余，避免重复存储相同数据（如学生表和班级表，通过班级 ID 关联，而非在学生表中重复存储班级名称），降低数据维护成本。

○一致性原则：统一数据命名规范、字段类型和编码格式（如日期格式统一为 YYYY-MM-DD，编码统一为 UTF-8），确保数据格式一致，便于跨模块、跨系统数据交互。

○完整性原则：通过主键、外键、非空约束、唯一约束等，确保数据的实体完整性、参照完整性和域完整性，避免无效数据、缺失数据和关联错误。

P48

○性能优先原则：设计过程中兼顾查询和写入性能，如高频查询字段建立索引，大字段（如文本、图片）单独存储，避免过度设计关联关系导致查询效率低下。

5.2 需求分析

需求分析是数据库设计的基础，也是最关键的阶段，核心是明确“业务需要存储什么数据、如何操作数据、数据有哪些约束”，为后续设计提供依据，需求分析不到位会导致整个数据库设计失败。

5.2.1 需求分析的内容

○业务需求：梳理业务流程（如用户注册、订单支付、成绩录入），明确每个业务流程的操作步骤、涉及的数据和业务规则（如订单支付后不可修改订单金额，成绩录入后需审核）。

○数据需求：确定需要存储的数据项、数据类型、数据范围和数据之间的关联关系（如用户数据包括用户 ID、姓名、手机号，订单数据包括订单 ID、用户 ID、订单金额，用户 ID 关联用户表和订单表）。

○操作需求：明确数据操作的类型（查询、插入、更新、删除）、频率和并发量（如电商订单表写入频率高，用户信息表查询频率高），以及操作的响应时间要求（如高频查询响应时间需≤100ms）。

○约束需求：明确数据的约束条件，包括实体完整性（如用户 ID 唯一）、参照完整性（如订单表的用户 ID 必须存在于用户表中）、域完整性（如手机号格式正确、年龄范围 1-120）和业务约束（如会员等级对应不同的折扣规则）。

○安全与性能需求：明确数据的安全等级（如核心业务数据需加密存储）、权限管控要求（如普通用户只能查询自己的订单），以及性能指标（如并发查询支持 1000QPS、数据存储容量支持 1000 万条记录）。

5.2.2 需求分析的方法与工具

○常用方法：

访谈法：与业务人员、产品经理、运维人员访谈，逐一确认业务流程和数据需求，记录访谈要点。

○问卷调查法：针对大规模业务场景（如多部门共用系统），设计问卷收集各部门的数据需求和操作习惯。

○流程分析法：梳理业务流程图，拆解每个环节的数据源、数据处理过程和数据输出，明确数据流转逻辑。

○原型法：搭建简单的数据模型原型，与业务人员确认需求，迭代优化，确保需求理解无偏差。

数据字典是需求分析的核心产出物，用于详细描述所有数据项的属性，包括：数据项名称、字段名、数据类型、长度、默认值、非空约束、唯一约束、关联表、业务说明等，确保后续设计人员统一理解数据含义。

5.3 概念结构设计

概念结构设计是将需求分析阶段梳理的业务需求，转化为独立于具体数据库管理系统（DBMS）的概念数据模型（CDM）的过程，核心是构建实体-联系（E-R）模型，屏蔽技术细节，聚焦数据之间的关联关系。概念结构设计的核心目标：准确映射业务需求，构建清晰、无冗余、逻辑连贯的概念模型，为后续逻辑结构设计提供基础。

5.3.1 核心概念

○实体（Entity）：客观存在、可相互区分的事物，是数据的载体，如用户、订单、商品、班级、学生等。实体分为强实体（无需依赖其他实体存在，如用户）和弱实体（需依赖强实体存在，如订单详情依赖订单）。

○属性（Attribute）：实体的特征，用于描述实体的具体信息，如用户的属性包括用户 ID、姓名、手机号、性别、注册时间等。属性分为：

简单属性：不可再拆分的属性（如姓名、手机号）。

○复合属性：可拆分为多个简单属性的属性（如地址可拆分为省、市、区、详细地址）。

○单值属性：一个实体的该属性只有一个值（如身份证号）。

○多值属性：一个实体的该属性有多个值（如用户的兴趣爱好可包括篮球、足球、读书）。

○派生属性：由其他属性推导得出的属性（如年龄可由出生日期推导得出）。

○码（Key）：用于唯一标识实体的属性或属性组合，分为：

候选码：能唯一标识实体的最小属性组合（如用户表中，用户 ID 可作为候选码，手机号若唯一也可作为候选码）。

○主码（主键，Primary Key）：从候选码中选择一个作唯一标识实体的属性/属性组合（如用户表选择用户 ID 作为主码）。

P50

○外码（外键，Foreign Key）：用于关联两个实体的属性，是一个实体的主码，对应另一个实体的属性（如订单表的用户 ID 是外键，关联用户表的用户 ID）。

○联系（Relationship）：实体之间的关联关系，由实体、联系类型和联系属性组成，如用户与订单的“下单”联系、学生与班级的“属于”联系。

5.3.2 联系的类型

根据实体之间的关联数量，联系分三类，核心是明确实体的基数约束（一个实体可关联另一个实体的数量）：

○一对一联系（1:1）：两个实体中，一个实体的一条记录只能关联另一个实体的一条记录，反之亦然。例如：用户与身份证的联系（一个用户对应一个身份证，一个身份证对应一个用户）、班级与班主任的联系（一个班级对应一个班主任，一个班主任对应一个班级）。

○一对多联系（1:N）：两个实体中，一个实体的一条记录可关联另一个实体的多条记录，而另一个实体的一条记录只能关联该实体的一条记录。例如：班级与学生的联系（一个班级有多个学生，一个学生属于一个班级）、用户与订单的联系（一个用户可下多个订单，一个订单属于一个用户），这是最常见的联系类型。

○多对多联系（M:N）：两个实体中，一个实体的一条记录可关联另一个实体的多条记录，反之亦然。例如：学生与课程的联系（一个学生可选多门课程，一门课程可被多个学生选择）、商品与订单的联系（一个订单可包含多个商品，一个商品可出现在多个订单中）。多对多联系需通过中间表（关联表）转化为两个一对多联系，中间表存储两个实体的主码作为外键。

5.3.3 E-R 模型的构建步骤

a. 识别实体：从需求分析中提取所有实体，明确实体的含义和范围，区分强实体和弱实体，给实体命名（命名需规范，贴合业务，避免歧义）。

b. 确定实体属性：为每个实体分配对应的属性，明确属性类型、约束条件，筛选出候选码，确定主码，处理多值属性、复合属性（如多值属性可单独作为一个实体，复合属性拆分为简单属性）。

c. 识别实体联系：梳理实体之间的业务关联，确定联系类型（1:1、1:N、M:N），明确联系的基数约束，给联系命名（如“下单”“选课”“属于”）。

d. 添加联系属性（可选）：若联系有自身的属性，需添加到联系中，如用户与订单的“下单”联系，可添加“下单时间”“支付方式”作联系属性。

e. 优化 E-R 模型：检查模型是否存在冗余（如重复实体、重复属性），调整联系类型，确保模型清晰、贴合业务，无逻辑错误，完成初步 E-R 图绘制。

f. 模型评审：组织业务人员、设计人员评审 E-R 模型，确认模型是否准确映射业务需求，优化不合理的设计，形成最终的概念数据模型。

5.3.4 E-R 模型的优化

优化的核心是消除冗余、简化模型，提升后续逻辑结构设计的效率，常用优化方法：

○消除冗余实体和属性：删除重复的实体，合并含义相同的属性；移除派生属性（无需存储，可通过其他属性推导）；将多值属性转化为独立实体（如用户的兴趣爱好，可创建“兴趣”实体，通过中间表关联用户实体）。

○调整联系类型：若多对多联系可拆分为更简单的联系，可进行拆分；若存在冗余联系（如 A 与 B 有联系，B 与 C 有联系，A 与 C 的联系可通过 B 推导），可删除冗余联系。

○拆分复杂实体：若一个实体包含过多属性，且属性之间存在不同的业务逻辑，可将其拆分为多个实体（如“用户”实体可拆分为“普通用户”和“管理员”实体，分别存储对应属性）。

5.4 逻辑结构设计

逻辑结构设计是将概念结构设计阶段构建的 E-R 模型，转化为具体 DBMS 支持的逻辑数据模型（LDM）的过程，核心是将实体、属性、联系转化关系模式（表结构），并优化关系模式，确保数据完整性和一致性，适配目标 DBMS（如 MySQL、Oracle）。

逻辑结构设计与具体 DBMS 相关，需结合 DBMS 的特性（如字段类型支持、约束支持、索引特性）进行设计，核心目标是生成可落地的表结构方案。

5.4.1 E-R 模型向关系模式的转化规则

转化的核心是遵循“实体转表、属性转字段、联系转关联”的原则，针对不同的实体类型和联系类型，采用不同的转化方法：

a. 强实体向关系模式的转化：

规则：一个强实体对应一个关系模式（表），实体的属性作为表的字段，实体的主码作为表的主键。

b. 示例：“用户”实体（主码：用户 ID，属性：用户 ID、姓名、手机号、性别、注册时间），转化为用户表（user），字段为 user_id（主键）、name、phone、gender、register_time。

c. 弱实体向关系模式的转化：

规则：一个弱实体对应一个关系模式，弱实体的属性作为表的字段，弱实体的主码由自身属性+所依赖强实体的主码组成（复合主键），同时将强实体的主码作为外键，关联强实体表。

d. 示例：“订单详情”是弱实体，依赖强实体“订单”（主码：订单 ID），弱实体属性：详情 ID、商品 ID、商品数量、商品单价，转化为订单详情表（order_detail），主键为（detail_id, order_id），order_id 作为外键关联订单表（order）的 order_id。

e. 一对一联系（1:1）向关系模式的转化（两种方法，可根据业务选择）：

方法一：将两个实体合并为一个表，其中一个实体的主码作为主键，另一个实体的主码作外键（唯一约束），确保一对一关联。

f. 方法二：两个实体分别转化为两个表，在其中一个表中添加另一个表的主码作为外键（唯一约束），实现一对一关联。

g 示例：“用户”与“身份证”是 1:1 联系，用户表（user，主键 user_id），身份证表（id_card，主键 id_card_id），在 id_card 表中添加 user_id 作为外键（唯一约束），关联 user 表，确保一个用户对应一个身份证。

h. 一对多联系（1:N）向关系模式的转化：规则：两个实体分别转化为两个表，在“多”的一方表中，添加“一”的一方表的主码作外键，实现关联，无需单独创建联系表。

i 示例：“班级”（1）与“学生”（N）是 1:N 联系，班级表（class，主键 class_id），学生表（student），在 student 表中添加 class_id 作外键，关联 class 表，实现一个班级对应多个学生。

j. 多对多联系（M:N）向关系模式的转化：

规则：需创建一个中间关联表，关联两个实体，中间表的字段为两个实体的主码（作外键，关联对应的实体表），中间表的主键可设为两个外键的复合主键，若联系有属性，需将联系属性作中间表的字段。

k. 示例：“学生”与“课程”是 M:N 联系，学生表（student，主键 student_id），课程表（course，主键 course_id），创建中间表“学生选课表”（student_course），字段为 student_id（外键）、course_id（外键）、score（联系属性，成绩），主键为（student_id, course_id），实现多对多关联。

5.4.2 关系模式的优化（规范化）

E-R 模型转化后的关系模式，可能存在数据冗余、插入异常、删除异常、更新异常等问题，需通过关系规范化进行优化，核心是遵循范式理论，常用的范式包括第一范式（1NF）、第二范式（2NF）、第三范式（3NF），更高阶的范式（如 BCNF）可根据业务需求选择是否应用。

5.4.2.1 范式定义

○第一范式（1NF）：最基础的范式，要求表中的每个字段都是原子的，不可再拆分，且字段名唯一，无重复字段。若表中存在复合属性（如地址拆分为省、市、区），需拆分后满足 1NF。不满足 1NF 的表无法进行后续规范化优化，也无法正常存储数据。

○第二范式（2NF）：在满足 1NF 的基础上，要求表中的每一个非主属性都完全依赖于主键（消除部分依赖）。若主键是复合主键，非主属性不能仅依赖于复合主键中的某一个字段。例如：学生选课表（student_id, course_id, student_name, score），主键为（student_id, course_id），student_name 仅依赖于 student_id（部分依赖），不满足 2NF，需拆分表，将 student_name 移至学生表。

○第三范式（3NF）：在满足 2NF 的基础上，要求表中的每一个非主属性都不传递依赖于主键（消除传递依赖），即非主属性之间不能存在依赖关系。例如：用户表（user_id, name, class_id, class_name），主键为 user_id, class_name 依赖于 class_id, class_id 依赖于 user_id, class_name 传递依赖于 user_id，不满足 3NF，需拆分表，将 class_name 移至班级表，用户表仅保留 class_id 作为外键。

5.4.2.2 规范化的目的与注意事项

○目的：消除数据冗余，避免插入异常（如无法插入无关联数据）、删除异常（如删除一条数据导致其他关联数据丢失）、更新异常（如修改一条数据需同时修改多条关联数据），提升数据维护效率。

P53

○注意事项：规范化并非越高越好，过高的范式（如 BCNF、4NF）会导致表数量过多，关联关系复杂，降低查询效率。实际设计中，通常优化到 3NF 即可，兼顾数据完整性和查询性能：若业务场景对查询性能要求极高，可适当降低范式，允许少量数据冗余，减少表关联。

5.4.3 逻辑结构设计的其他优化

除了关系规范化，还需结合业务场景和 DBMS 特性，对逻辑结构进行优化，提升性能和可维护性：

○字段类型优化：根据数据的实际范围选择合适的字段类型，避免过度占用存储空间，提升查询和存储效率。例如：存储手机号用 CHAR（11）（固定长度，查询更快），存储年龄用 TINYINT（范围 1-120，占用 1 字节），存储日期用 DATE/DATETIME（避免用字符串存储）。

○约束优化：合理设置约束，确保数据完整性，同时避免过度约束影响性能。例如：主键、外键、唯一约束必须设置，非空约束根据业务需求设置；避免使用过多的检查约束（如复杂的条件判断），可通过应用程序实现部分业务约束。

○索引设计（初步）：针对高频查询字段，初步设计索引（如用户表的手机号字段、订单表的下单时间字段），提升查询速度；避免给高频写入字段（如订单表的订单金额）建立过多索引，防止写入性能下降。

○分表分库规划（可选）：若业务数据量较大（如预计超过 1000 万条），需提前规划分表分库策略，如按时间分表（订单表按月份分表）、按地域分库，避免单表数据量过大导致性能下降。

逻辑结构设计完成后，输出《逻辑数据模型设计说明书》，核心内容包括：关系模式清单（表结构）、字段说明、主键/外键定义、约束条件、索引设计方案、数据字典（完善版）、表关联关系图等，为后续物理结构设计提供依据。

5.5 物理结构设计

物理结构设计是将逻辑数据模型转化为具体的数据库物理结构的过程，核心是结合目标 DBMS 的特性和硬件环境，确定数据的存储结构、存储位置、索引策略、分区策略等，优化数据库的存储性能和访问性能，是数据库设计落地的关键阶段。

物理结构设计与 DBMS、硬件环境（如服务器配置、存储设备）密切相关，需针对性设计，核心目标是提升数据读写性能、降低存储成本、保障数据可靠性。

5.5.1 核心设计内容

○存储结构设计：

表空间设计（Oracle 专属）：根据数据的重要性和访问频率，划分不同的表空间（如系统表空间、用户表空间、索引表空间、临时表空间），便于管理和优化；将核心业务表和索引存储在高性能存储设备上，临时数据存储在普通存储设备上。

P54

○数据文件配置：设置数据文件的大小、增长方式（如自动增长、固定大小），避免数据文件过大导致管理困难，或增长过慢导致空间不足；多个数据文件可分散存储在不同的磁盘上，提升 I/O 性能。

○索引设计（细化）：

索引类型选择：根据查询场景选择合适的索引类型，如 MySQL 的 B+树索引（适用于范围查询、排序查询）、哈希索引（适用于等值查询）、全文索引（适用于文本搜索）；Oracle 的 B 树索引、位图索引（适用于低基数字段，如性别）。

○索引优化原则：高频查询字段优先建立索引，低频查询字段无需建立索引；避免给高频写入字段建立过多索引（索引会增加写入开销）；合理设计联合索引（如查询条件“用户 ID+下单时间”，可建立联合索引，提升查询速度）；定期清理无效索引，优化索引碎片。

○分区设计：

适用场景：单表数据量较大（如超过 1000 万条），查询场景具有明显的分区特征（如按时间、地域查询）。

○分区类型选择：按时间分区（如订单表按年/月/日分区）、按范围分区（如按金额范围分区）、按列表分区（如按地域分区）、按哈希分区（均匀分布数据），根据业务场景选择合适的分区方式。

○优点：提升查询速度（仅扫描目标分区，无需扫描全表）；便于数据管理（如删除历史分区数据，无需删除全表）；平衡 I/O 负载，提升存储效率。

○存储参数配置：

缓存配置：设置数据库缓存大小（如 MySQL 的 innodb_buffer_pool_size、Oracle 的 SGA），提升数据读取速度（缓存常用数据，减少磁盘 I/O）。

○日志配置：设置事务日志的大小、刷盘策略（如 MySQL 的 innodb_flush_log_at_trx_commit），平衡数据可靠性和写入性能；日志文件可分散存储在不同磁盘上，避免日志写入瓶颈。

5.5.2 物理结构设计的优化原则

○性能优先：优先保障高频业务的读写性能，如电商的订单查询、支付操作，通过索引、分区、缓存优化，降低响应时间。

○可靠性保障：设置合理的存储冗余（如磁盘阵列）、日志策略，确保数据不丢失；核心数据可配置备份策略，与物理结构设计协同。

○可扩展性：预留存储空间和配置余量，支持业务数据量增长；分区、分表策略需适配后续业务扩展，避免频繁调整物理结构。

P55

○成本平衡：结合业务需求选择合适的硬件和存储方案，避免过度配置导致成本浪费；高频访问数据用高性能存储，低频访问数据用普通存储。

5.5.3 物理结构设计文档

物理结构设计完成后，输出《物理数据模型设计说明书》，核心内容包括：DBMS 选型说明、表空间配置、数据文件配置、索引详细方案、分区方案、缓存配置、日志配置、存储设备规划等，作为数据库实施的依据。

5.6 数据库实施

数据库实施是将物理结构设计的成果落地的过程，核心是创建数据库、表、索引、约束等对象，导入测试数据，验证数据库结构的正确性和可用性，为后续应用开发和上线做准备。

5.6.1 实施步骤

环境准备：搭建数据库服务器环境，安装目标 DBMS（如 MySQL、Oracle），配置服务器参数（如内存、CPU、磁盘存储），根据物理结构设计文档配置 DBMS 参数（如缓存、日志、表空间），确保环境符合设计要求。

创建数据库对象：使用 SQL 语句或 DBMS 自带工具（如 MySQL 的 Navicat、Oracle 的 PL/SQL Developer），创建数据库、表、索引、约束、视图、存储过程、触发器等对象，严格遵循物理结构设计文档的规范，确保对象结构正确。

数据导入：导入测试数据（模拟业务数据），验证数据存储和关联的正确性；导入数据时需注意数据格式、约束条件，避免导入无效数据；可使用 DBMS 自带的导入工具（如 mysqldump、expdp），提升数据导入效率。

结构与功能测试：

结构测试：检查表结构、字段类型、约束、索引是否符合设计要求，验证主键、外键的关联正确性，检查分区、表空间配置是否生效。

功能测试：模拟业务操作（查询、插入、更新、删除），验证数据库是否支持所有业务需求，检查数据一致性和完整性，测试查询响应时间、并发性能是否满足指标。

性能优化调整：根据测试结果，调整物理结构设计，如优化索引、调整缓存配置、修改分区策略，提升数据库性能；解决测试中发现的问题（如数据冗余、查询缓慢、约束冲突），确保数据库符合业务需求。

5.6.2 常用实施工具

•SQL 执行工具：Navicat、PL/SQL Developer、DBeaver，用于编写和执行 SQL 语句，创建数据库对象、导入导出数据。

○建模工具：PowerDesigner、Erwin，可将物理数据模型直接生成 SQL 脚本，执行脚本创建数据库对象，提升实施效率。

○数据导入导出工具：mysqldump（MySQL）、expdp/impdp（Oracle）、SQL Server 的 Bcp，用于批量导入导出数据，适配大数据量场景。

○性能测试工具：JMeter、LoadRunner，用于模拟并发请求，测试数据库的并发性能、响应时间，找出性能瓶颈。

5.7 数据库运行与维护

数据库上线后，需进行长期的运行与维护，确保数据库稳定、高效运行，及时处理故障，适配业务迭代，核心是“监控、优化、备份、故障处理”，保障数据安全和业务连续性。

5.7.1 日常维护内容

○监控管理：

性能监控：监控数据库的 CPU 使用率、内存占用、磁盘 I/O、并发连接数、查询响应时间、锁等待情况，设置阈值告警（如并发连接数超过阈值时触发告警），及时发现性能瓶颈。

○空间监控：监控数据库存储空间的使用情况，包括表空间、数据文件、日志文件的占用率，预留足够的存储空间，避免空间不足导致业务中断；定期清理日志文件、临时数据，释放存储空间。

○日志监控：监控数据库的错误日志、事务日志、操作日志，及时发现错误（如连接失败、数据损坏、锁冲突），追溯异常操作，排查问题原因。

○备份与恢复维护：

定期执行备份：按照备份策略，自动或手动执行全量、差异、增量备份，确保备份文件完整有效；定期校验备份文件，测试恢复流程，更新恢复手册。

备份文件管理：异地存储备份文件，定期清理过期备份文件，防止备份文件丢失或占用过多存储空间；记录备份日志，便于审计和问题追溯。

○性能优化：

SQL 语句优化：定期分析慢查询日志，优化低效 SQL 语句（如优化查询条件、添加索引、避免全表扫描），提升查询速度；规范 SQL 语句编写，避免不合理的关联、排序操作。

索引优化：定期检查索引使用情况，清理无效索引、冗余索引，优化索引碎片（如 MySQL 的 OPTIMIZE TABLE、Oracle 的 ALTER INDEX REBUILD），提升索引性能。

参数调整：根据数据库运行状态，调整 DBMS 参数（如缓存大小、日志刷盘策略、并发连接数），适配业务负载变化，提升整体性能。

○安全维护：

权限管理：定期审计数据库用户权限，回收过期权限、冗余权限，禁止非授权访问；设置复杂密码，定期更换密码，防止密码泄露。

P57

数据安全：核心业务数据加密存储（如敏感信息加密、传输加密），防止数据泄露；定期检查数据完整性，发现数据损坏及时恢复。

漏洞修复：关注 DBMS 安全漏洞，及时安装补丁，更新 DBMS 版本，防止恶意攻击；配置防火墙，限制数据库服务器的访问 IP，提升安全性。

5.7.2 故障处理

数据库运行过程中，可能出现各类故障（如硬件故障、软件故障、数据损坏、锁冲突），需建立完善的故障处理流程，快速响应、解决故障，减少业务损失：

a. 故障发现：通过监控告警、业务反馈，及时发现数据库故障，记录故障现象（如报错信息、业务中断情况、故障发生时间）。

b. 故障诊断：排查故障原因，确定故障类型（如硬件故障、数据损坏、锁冲突），判断数据丢失范围和业务影响范围。

c. 故障处理：根据故障类型，执行对应的处理方案（如重启服务、恢复备份、清理锁、修复数据），优先恢复核心业务，减少停机时间。

d. 故障复盘：故障解决后，分析故障原因，总结处理经验，优化维护策略和监控方案，避免同类故障再次发生。

5.7.3 业务迭代适配

随着业务迭代，数据库结构可能需要调整（如新增字段、新增表、修改约束），需遵循规范的变更流程，避免影响现有业务：

a. 变更申请：业务部门提交数据库结构变更申请，说明变更内容、变更原因、影响范围。

b. 变更评审：设计人员、运维人员、开发人员评审变更方案，确认变更可行性、对现有业务的影响，优化变更方案。

c. 变更实施：在测试环境验证变更方案，确认无误后，在业务低峰期（如凌晨）执行变更，备份当前数据库结构和数据，便于回滚。

d. 变更验证：变更完成后，测试业务功能，验证数据库结构变更是否符合要求，检查数据一致性和性能。

e. 变更记录：记录变更内容、实施时间、操作人、测试结果，形成变更日志，便于后续追溯和问题排查。

5.8 数据库设计案例（简化版）

以电商平台的订单管理模块为例，展示数据库设计的完整流程（简化版），贴合实际业务场景，便于理解：

5.8.1 需求分析

核心业务：用户下单、订单支付、订单查询、订单修改，涉及用户、订单、商品、订单详情四个核心业务对象。

数据需求：

1. 用户：用户 ID、姓名、手机号、注册时间（主键：用户 ID）；

2. 商品：商品 ID、商品名称、商品单价、库存（主键：商品 ID）；

P58

3. 订单：订单 ID、用户 ID、下单时间、支付金额、支付状态（主键：订单 ID）；

4. 订单详情：详情 ID、订单 ID、商品 ID、商品数量、商品单价（依赖订单，主键：详情 ID+订单 ID）。

约束需求：订单的用户 ID 关联用户表，订单详情的订单 ID 关联订单表、商品 ID 关联商品表；支付状态只能是“未支付”“已支付”“已取消”。

5.8.2 概念结构设计（E-R 模型）

实体：用户、商品、订单、订单详情（弱实体）；

联系：用户与订单（1:N）、订单与订单详情（1:N）、商品与订单详情（1:N）、用户与商品无直接联系。

5.8.3 逻辑结构设计（关系模式）

转化为 MySQL 表结构，优化至 3NF：

1.用户表（user）：user_id （INT，主键）、name （VARCHAR（50））、phone （CHAR（11），唯一）、

register_time (DATETIME);

2. 商品表（product）：product_id （INT，主键）、product_name （VARCHAR（100））、price（DECIMAL（10,2））、stock（INT）；

3. 订单表（order）：order_id （INT，主键）、user_id （INT，外键关联 user.user_id）、order_time（DATETIME）、pay_amount （DECIMAL（10,2））、pay_status （VARCHAR（20））；

4. 订单详情表（order_detail）： detail_id（INT）、order_id（INT，外键关联 order.order_id）、product_id（INT，外键关联 product.product_id）、quantity （INT）、unit_price （DECIMAL（10,2）），主键（detail_id, order_id）。

5.8.4 物理结构设计

MySQL 环境下的物理设计：

1.索引：order 表的 user_id、order_time 建立索引；order_detail 表的 order_id、product_id 建立联合索引；product 表的 product_id 建立主键索引；

2. 字段优化：pay_status 用 ENUM 类型（'未支付','已支付','已取消'），减少存储空间；

3. 分区：订单表按 order_time 按月分区，提升历史订单查询速度；

4.缓存：设置 innodb_buffer_pool_size 为服务器内存的 50%，缓存常用订单数据和商品数据。

5.8.5 实施与维护

1. 实施：执行 SQL 脚本创建表、索引，导入测试数据，测试下单、查询功能；

2. 维护：定期备份订单数据（每日全量+每 6 小时增量），监控订单查询性能，优化慢查询，定期清理过期订单数据。

通过该案例，可清晰看到数据库设计的全流程，核心是贴合业务需求，逐步细化，兼顾数据完整性和性能。

5.9 数据库技术发展与应用场景拓展

5.9.1 主流数据库类型及应用场景

随着业务的发展，数据库类型不断丰富，不同类型的数据库适配不同的业务场景，核心分类及应用：

P59

○关系型数据库（RDBMS）：

代表产品：MySQL、Oracle、SQL Server、PostgreSQL；

核心特性：支持 ACID 事务、结构化数据存储、SQL 查询、主键外键关联，数据一致性强；

应用场景：核心业务系统（如电商订单、金融交易、政务系统），适合结构化数据、对数据一致性要求高的场景。

○非关系型数据库（NoSQL）：

代表产品：MongoDB（文档型）、Redis（键值型）、MongoDB（文档型）、HBase（列族型）、Neo4j（图数据库）；

核心特性：无需固定表结构、支持非结构化/半结构化数据、高并发、高可用，灵活性强；

应用场景：MongoDB 适用于博客、电商评论等文档型数据；Redis 适用于缓存、计数器、会话存储；HBase 适用于大数据量、高并发写入场景（如日志存储）；Neo4j 适用于社交网络、知识图谱等关联关系复杂的场景。

•NewSQL 数据库：

代表产品：TiDB、CockroachDB、OceanBase；

核心特性：融合关系型数据库的 ACID 事务、SQL 查询能力与非关系型数据库的高并发、高可用、水平扩展特性，解决传统 RDBMS 扩展难、NoSQL 数据一致性弱的痛点，支持分布式架构，可应对海量数据场景；

应用场景：互联网大厂核心业务（如电商交易、支付结算）、政务大数据平台、金融风控系统等，适合需要兼顾数据一致性与海量数据存储、高并发访问的场景。

•时序数据库：

代表产品：InfluxDB、Prometheus、TimeScaleDB；

核心特性：专门用于存储和分析时序数据（按时间顺序生成的数据，如设备监控数据、日志数据），支持高吞吐量写入、时间维度快速查询、数据自动过期清理，优化时序数据的存储和计算效率；

应用场景：物联网设备监控、系统监控告警、金融行情分析、环境监测等，适合数据按时间高频产生、需长期存储并进行时序分析的场景。

•图数据库：

代表产品：Neo4j、NebulaGraph、ArangoDB；

核心特性：以“节点-关系”模型存储数据，擅长处理实体间复杂的关联关系，可快速遍历多跳关联数据，无需复杂关联查询，支持图算法（如最短路径、社区发现）；

应用场景：社交网络（好友推荐、关系链分析）、知识图谱（学术溯源、智能问答）、金融风控（欺诈检测、关联风险识别）等，适合实体关联复杂、需深度挖掘关系的场景。

5.9.2 数据库技术发展趋势

随着大数据、人工智能、云计算、物联网等技术的快速发展，数据库技术呈现出多维度融合、智能化、场景化的发展趋势，核心方向如下：

•分布式架构成为主流：传统单机数据库难以应对海量数据存储和高并发访问需求，分布式数据库通过数据分片、副本机制，实现水平扩展和高可用，既能承载 PB 级数据，又能支撑百万级并发请求，成为互联网、金融等行业的核心选择，且分布式技术逐渐下沉，降低中小企业使用门槛。

P60

•多模型融合发展：单一类型数据库难以适配复杂业务场景，多模型数据库（如 ArangoDB、MongoDB 5.0+）可同时支持关系型、文档型、图型等多种数据模型，无需为不同数据类型部署多个数据库，简化架构设计，提升开发和运维效率，适配多元化业务数据存储需求。

•智能化运维与优化：结合人工智能和机器学习技术，实现数据库的智能监控、故障预测、自动调优，如自动优化 SQL 语句、动态调整缓存和索引、预测存储空间不足和性能瓶颈，减少人工运维成本，提升数据库运行稳定性，适配大规模分布式数据库的运维需求。

•云原生数据库快速崛起：依托云计算平台，云原生数据库（如 AWS Aurora、阿里云 RDS、腾讯云 CDB）实现弹性扩展、按需付费，支持容器化部署和微服务架构，与云存储、云计算深度融合，无需用户关注底层硬件和环境配置，降低数据库部署和运维成本，成为中小企业和互联网企业的首选。

•数据安全与隐私保护强化：随着数据安全法规的完善（如《数据安全法》《个人信息保护法》），数据库逐渐内置数据加密、访问控制、脱敏、审计等安全功能，支持隐私计算（如联邦学习），实现“数据可用不可见”，兼顾数据利用与隐私保护，适配金融、政务、医疗等敏感数据存储场景。

5.9.3 数据库应用场景拓展

随着数据库技术的迭代，其应用场景已从传统的企业数据管理，延伸到各行各业的核心业务，成为数字化转型的核心支撑，典型拓展场景如下：

•物联网（IoT）场景：依托时序数据库和 NoSQL 数据库，存储物联网设备产生的海量监控数据（如温度、湿度、设备运行状态），支持高并发写入和时序分析，实现设备故障预警、能耗优化、智能调度，广泛应用于工业物联网、智能家居、智慧交通等领域。

•人工智能与大数据场景：结合 NewSQL 和分布式数据库，存储和处理 AI 训练所需的海量标注数据、样本数据，支持高效的数据查询和批量处理；通过图数据库挖掘数据关联关系，为 AI 推荐系统、智能决策提供支撑；时序数据库用于 AI 模型的监控和迭代优化。

•金融科技场景：依托高可用、高一致性的分布式数据库和 NewSQL 数据库，支撑高频交易、支付结算、风控审计等核心业务，确保交易数据不丢失、不重复，同时通过时序数据库分析用户交易行为，识别欺诈风险，适配金融行业的合规要求和高并发需求。

•政务与公共服务场景：采用分布式数据库和云原生数据库，构建政务大数据平台，整合人口、社保、医疗、政务办理等多维度数据，支持跨部门数据共享和高效查询，优化政务服务流程（如线上审批、智能办税），提升公共服务效率，同时保障政务数据的安全和一致性。

•工业互联网场景：通过时序数据库存储工业设备运行日志、生产数据，结合图数据库分析设备间的关联关系，实现生产流程优化、设备故障预测、质量管控；分布式数据库支撑工业大数据的集中管理和跨厂区数据共享，推动工业数字化转型。

5.9.4 数据库选型核心原则

数据库选型是数据库设计和应用的前提，需结合业务需求、数据特性、性能要求、运维成本等多维度考量，核心原则如下：

•贴合业务需求优先：根据业务数据类型（结构化、非结构化、时序数据）、并发量、数据量、一致性要求选型，如核心交易业务优先选择支持 ACID 的关系型或 NewSQL 数据库，非结构化数据优先选择文档型 NoSQL 数据库。

P61

•平衡性能与成本：高并发、海量数据场景需选择分布式、高扩展的数据库，但需兼顾部署和运维成本；中小规模业务可选择云原生数据库或开源数据库（如 MySQL、MongoDB），降低成本的同时满足业务需求。

•考虑可扩展性和兼容性：选型时预留扩展空间，适配业务数据量和并发量的增长；优先选择支持 SQL 标准、生态完善的数据库，便于与现有系统集成，降低开发和迁移成本。

•重视安全与可靠性：核心业务、敏感数据场景，优先选择支持数据加密、备份恢复、故障自动切换的数据库，确保数据安全和业务连续性，满足合规要求。

•匹配运维能力：结合团队运维水平选型，复杂分布式数据库（如 TiDB、Oracle）对运维能力要求较高，中小团队可选择运维简单的开源数据库或云原生数据库，减少运维压力。

5.10 数据库设计常见问题与解决方案

在数据库设计和应用过程中，易出现表结构冗余、性能瓶颈、数据不一致等问题，结合实际场景总结常见问题及针对性解决方案，助力规避设计误区、优化数据库性能。

5.10.1 常见设计问题及解决方案

•问题 1：表结构冗余，出现插入、更新、删除异常

成因：未严格遵循规范化原则，表中存在重复字段、传递依赖或部分依赖，未合理拆分表结构。

解决方案：按 3NF 规范优化表结构，拆分冗余表，消除部分依赖和传递依赖；移除重复字段，通过外键关联实现数据共享；避免过度冗余，同时兼顾查询性能，必要时可保留少量合理冗余减少表关联。

•问题 2：查询性能低下，出现全表扫描

成因：未针对高频查询字段建立索引，或索引设计不合理（如冗余索引、无效索引）；表数据量过大，未做分区处理；SQL 语句编写不规范（如使用 SELECT *、复杂子查询）。

解决方案：为高频查询字段、外键字段建立索引，优化联合索引顺序（遵循“最左前缀原则”）；定期清理无效索引、优化索引碎片；大表按时间、范围等维度分区；优化 SQL 语句，避免全表扫描和复杂子查询，使用分页查询减少数据返回量。

•问题 3：数据一致性受损，出现外键冲突、数据缺失

成因：未合理设置约束（主键、外键、唯一约束、非空约束）；事务未提交或回滚机制不合理；并发操作未做好控制，出现丢失修改等异常。

解决方案：严格设置主键、外键约束，确保实体完整性和参照完整性；根据业务需求设置非空、唯一约束，避免无效数据插入；合理控制事务粒度，遵循 ACID 原则，避免长事务；通过锁机制、事务隔离级别或 MVCC，控制并发操作，避免数据一致性问题。

•问题 4：数据库扩展困难，无法应对数据量增长

成因：初期设计未考虑数据量增长，采用单机架构，未规划分表分库或分区策略；表结构设计僵化，难以适配业务迭代。

解决方案：初期设计预留扩展空间，大表提前规划分区策略；数据量激增时，采用分表分库（水平分表、垂直分表）或迁移至分布式数据库；设计灵活的表结构，新增字段时避免影响现有业务，适配业务迭代需求。

•问题 5：写入性能低下，出现锁等待、阻塞

成因：高频写入字段建立过多索引，索引更新开销过大；事务执行时间过长，占用锁资源；并发写入量过高，未做分流处理。

解决方案：减少高频写入字段的索引数量，仅保留必要索引；优化事务逻辑，缩短事务执行时间，减少锁持有时间；采用读写分离架构，分流写入压力；避免批量写入操作集中执行，拆分批量任务，错峰执行。

5.10.2 设计优化禁忌

•禁忌 1：过度规范化，导致表数量过多、关联复杂，大幅降低查询性能；

•禁忌 2：忽视索引设计或滥用索引，既影响写入性能，又无法提升查询效率；

•禁忌 3：不设置约束或过度依赖应用程序控制数据完整性，导致数据库层面数据错乱；

•禁忌 4：表字段类型选择不合理（如用字符串存储日期、用大字段存储少量数据），浪费存储空间、影响性能；

•禁忌 5：忽视备份与恢复策略，未定期测试恢复流程，导致数据丢失后无法快速还原。
